<LessonSteps>
  <Step id="hook" title="Hook">
    Sooner or later, a database leaks. The question that matters is what the attacker finds in the `users` table: passwords they can type into other sites, or something close to useless.

    <Analogy title="The fingerprint">
      A good lock keeps a scan of your fingerprint, never a copy of your finger. It can tell that a finger matches, but nobody can rebuild the finger from the scan. Password storage works the same way: keep something that can confirm a password, never the password.
    </Analogy>
  </Step>

  <Step id="hash" title="Hash, don't store">
    Three ways to keep a password, from worst to best.

    1. **Plaintext.** One leak exposes every account, and every other site where users reused the password.
    2. **Encryption.** Better looking, same outcome. The app must be able to decrypt, so the key lives where the app runs, and an attacker who got the database often gets the key too.
    3. **Hashing.** A one-way function. The server stores the hash, and at login it hashes the attempt and compares. There is nothing to decrypt.

    But "hashed" is not enough. MD5, SHA-1 and SHA-256 are designed to be **fast**. That is great for checking a download and terrible here, because a single GPU can test billions of guesses per second against a stolen hash, and most real passwords fall to a dictionary in minutes.

    <Callout type="security">
      Never invent your own scheme, and never use a general-purpose hash (MD5, SHA-1, SHA-256, even SHA-3) on its own for passwords. Use a password hashing function: argon2id, scrypt, bcrypt or PBKDF2.
    </Callout>
  </Step>

  <Step id="salt" title="Salt and cost">
    Two ingredients turn a hash into a password hash.

    A **salt** is a random value, unique per password, stored right next to the hash. It is not secret. It makes every hash different, so one precomputed table cannot crack all users, and two people with the same password no longer look the same.

    A **cost** makes each guess expensive on purpose. Argon2id is also **memory-hard**: every guess needs a large block of RAM, which takes away the advantage of GPUs and custom chips.

    | Algorithm | Recommended setting (OWASP Password Storage cheat sheet) | Notes |
    |---|---|---|
    | argon2id | m=19456 KiB (19 MiB), t=2, p=1 | First choice. The lab uses exactly this. |
    | scrypt | N=2^17, r=8, p=1 | Memory-hard too. |
    | bcrypt | cost 10 or more | Truncates input at 72 bytes. Fine for legacy systems. |
    | PBKDF2-HMAC-SHA256 | 600,000 iterations or more | For FIPS-bound systems. Not memory-hard. |

    A hash is usually stored as one self-describing **PHC string**, so the verifier never has to guess the settings:

    ```text
    $argon2id$v=19$m=19456,t=2,p=1$c2FsdHNhbHRzYWx0$aGFzaGhhc2hoYXNo
    ```

    Read it left to right: the algorithm, the version, the memory (KiB), time and parallelism settings, then the salt and the hash, both in unpadded base64.

    Because the parameters travel with the hash, you can raise the cost later and rehash each user the next time they log in.

    **What about the password rules themselves?** NIST SP 800-63B says: allow long passphrases (at least 64 characters), accept spaces and Unicode, do not force "one uppercase, one symbol" composition rules, do not force periodic rotation, and reject passwords found in breach lists or common-password lists. The lab accepts 8 to 128 characters. The latest revision raises the single-factor minimum to 15, so treat the lab as a minimum, not a recommendation.
  </Step>
