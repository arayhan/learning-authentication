<LessonSteps>
  <Step id="hook" title="Hook">
    You are signed in to your bank in one tab. In another tab you open a page that promises a free cruise. Nothing visibly happens, and your balance drops anyway.

    <Analogy title="The forged signature">
      Someone slips a letter in front of your bank, written by them, carrying a signature that looks like yours. The bank sees a familiar signature and pays out. It never asks whether you actually wrote the letter.
    </Analogy>
  </Step>

  <Step id="attack" title="The attack">
    **Cross-site request forgery (CSRF)** makes a victim's browser send a request they never intended, while it carries their cookie.

    It works because of one browser habit: cookies are **ambient credentials**. The browser attaches the cookies for `bank.example` to every request going to `bank.example`, no matter which page caused the request. The bank cannot tell a click on its own page from a form hidden on another site.

    <SequenceFlow flow={flows.csrfAttack} />

    Three ingredients are needed. Remove any one and the attack fails:

    1. The app authenticates with a **cookie** the browser sends by itself.
    2. There is a **state-changing request** (transfer money, change email).
    3. The attacker can **predict every parameter** of that request.

    Note what the attacker does **not** get: the response. CSRF is blind. It can cause actions, not read data, which is why it targets state changes.
  </Step>

  <Step id="defenses" title="Defenses">
    Defenses stack, and each one blocks the attack at a different point.

    | Defense | How it stops the forged request | Watch out for |
    |---|---|---|
    | `SameSite=Lax` cookie | The browser does not send the cookie on cross-site POSTs or subrequests | Subdomains count as the same site. Lax still sends cookies on cross-site top-level **GET** navigations, so never change state on GET. |
    | **CSRF token** (synchronizer) | A per-session secret must come back in a header or field. Attackers cannot read it, so they cannot send it. | Must be unpredictable, tied to the session, and compared in constant time |
    | **Origin check** | Reject unsafe requests whose `Origin` (or `Sec-Fetch-Site`) is not your own site | Do not rely on `Referer` alone. Be strict about which origins are allowed |
    | Custom header + CORS | A JSON `fetch` with a custom header triggers a CORS preflight that other origins fail | A weak fallback. Do not rely on it as your only defense |

    One caveat on `SameSite`: modern Chrome treats a cookie with no `SameSite` attribute as `Lax` by default. In the simulator, "no SameSite" therefore models older browsers or an explicit `SameSite=None`.

    The lab uses the **synchronizer token** pattern. Each session gets its own random CSRF token (you saw it in the `/login` response body). The browser's own JavaScript sends it back in an `X-CSRF-Token` header on every request that changes state, and the server compares it with the one stored for that session.

    <Callout type="security">
      **CORS is not a CSRF defense.** CORS decides who may *read* a cross-origin response. A cross-site form POST is a "simple request": it is still sent, with cookies, and the damage happens whether or not anyone reads the reply.
    </Callout>

    <Callout type="warn">
      If your own subdomains are not all trusted, or an attacker can run script on one of them, `SameSite` will not separate them from your app: same registrable domain means same site. The token and Origin check carry the load. And an **XSS** bug on your own origin defeats every CSRF defense, because the attacker's script can read the token like any other script.
    </Callout>

    <Callout type="info">
      Worth asking of your own setup: do **sso-frontend** and **sso-backend** live on sibling subdomains of one domain, and which cookies does the browser send between them? If so, `SameSite` alone does not isolate them from other things on that domain, so check that state-changing endpoints verify a token or `Origin`.
    </Callout>
  </Step>

    Two requests, one cookie, two different outcomes. Log in, then try the transfer without and with the CSRF token.

    <LabConsole

        { label: "Log in", method: "POST", path: "/login", body: { email: "{{email}}", password: "correct horse battery" } },
        { label: "Transfer, no token", method: "POST", path: "/transfer", body: { to: "bob@example.com", amount: 25 } },
        { label: "Transfer, with token", method: "POST", path: "/transfer", headers: { "X-CSRF-Token": "{{csrfToken}}" }, body: { to: "bob@example.com", amount: 25 } },
      ]}
    />

    The first transfer carries your valid session cookie and still gets `403 {"error":"csrf"}`. That is what a forged request looks like to a protected server: right cookie, missing secret.

    The second one adds `X-CSRF-Token`, taken from the response to `/login`, and returns `200`. Only code running in the bank's own page could have known that value.

    <Callout type="info">
      A subtle point about the lab: `/transfer` only accepts `application/json`, and a cross-site HTML form cannot send that type. So a plain form attack would already fail on a parsing error. That is an accident of the API, not a defense to count on. Parsers get lenient and endpoints get added, so keep the token.
    </Callout>
  </Step>

  <Step id="breakit" title="Break it">
    Now play the attacker's side and see what happens when the check is gone. The button below sends `X-Lab-Mode: vulnerable`, which makes the lab skip the CSRF check. It is a stand-in for a server that forgot it.

    <LabConsole
      lab="01"
      actions={[
        { label: "Register", method: "POST", path: "/register", body: { email: "{{randomEmail}}", password: "correct horse battery" } },
        { label: "Log in", method: "POST", path: "/login", body: { email: "{{email}}", password: "correct horse battery" } },
        { label: "Forged transfer, no token", method: "POST", path: "/transfer", body: { to: "mallory@example.com", amount: 500 }, vulnerable: true },
        { label: "Transfer, no token (secure)", method: "POST", path: "/transfer", body: { to: "mallory@example.com", amount: 500 } },
      ]}
    />

    With the check skipped, the forged request returns `200`: the cookie alone was enough. Run the secure version of the same request and it returns `403`.

    The point of the exercise: the **only** thing separating "attacker moves money" from "attacker is refused" is one server-side comparison.
