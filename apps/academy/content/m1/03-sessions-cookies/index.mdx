<LessonSteps>
  <Step id="hook" title="Hook">
    HTTP has no memory. Every request arrives as a stranger, yet the app somehow remembers you across a hundred page loads without asking for your password again.

    <Analogy title="The coat-check ticket">
      You hand over your coat once and get a numbered ticket. Showing the ticket gets the coat back, and nobody asks who you are again. But anyone holding the ticket gets the coat, so the number must be impossible to guess.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    After a successful login the server creates a **session**: a record that says "this is Alice, valid until 15:30". It gives the browser a random **session id** to point at that record, and the browser sends the id back on every request.

    The id travels in a **cookie**. The server sets it once with `Set-Cookie`, and from then on the browser attaches it automatically to every request to that site.

    <SequenceFlow flow={flows.sessionCookie} />

    The session id is a **bearer secret**: whoever presents it is treated as Alice. That one fact drives every rule in this lesson. It must be random, protected in storage, protected in transit, and hidden from scripts.
  </Step>

  <Step id="cookie" title="Anatomy of a cookie">
    This is the exact header the lab sends back from `/login`:

    ```text
    Set-Cookie: sid=Xk3q9ZmB1vW8eYrT5uLpA7sD0fGhJcN4iOaE6bQwVyU; Path=/; Max-Age=3600; HttpOnly; SameSite=Lax
    ```

    Each attribute is a safety feature:

    | Attribute | What it does | Why you want it |
    |---|---|---|
    | `HttpOnly` | Hides the cookie from `document.cookie` | An injected script cannot read and ship off the session id |
    | `Secure` | Sends the cookie over HTTPS only | Stops it travelling in clear text on a network you do not control |
    | `SameSite=Lax` | Withholds the cookie on cross-site subrequests and POSTs | Cuts off most CSRF (lesson 5) |
    | `Path=/` | Which URLs get the cookie | Keep it broad for a session |
    | `Max-Age=3600` | Lifetime in seconds | A cookie that expires, and a session that expires with it |
    | no `Domain` | A host-only cookie | Subdomains do not receive it |

    <Callout type="warn">
      The lab leaves out `Secure` only because it runs on plain `http://localhost`. In production `Secure` is required. The strongest form is the `__Host-` prefix, for example `__Host-sid`: the browser then insists on `Secure`, `Path=/` and no `Domain`.
    </Callout>

    A word on **same-site** versus **same-origin**, because it trips people up. A *site* is the scheme plus the registrable domain, and ports are ignored. So `localhost:3000` (this academy) and `localhost:4101` (the lab) are **same-site**, which is why the lab's cookie flows to and from your browser even though the ports differ.
  </Step>

  <Step id="server" title="What the server keeps">
    A good session store follows three rules.

    1. **Random id.** 32 bytes from a cryptographically secure generator, base64url-encoded. OWASP asks for at least 64 bits of entropy, and 256 bits makes guessing hopeless. The id has no meaning: it is a lookup key, not a data container.
    2. **Store only the hash.** The `sessions` table holds `sha256(id)`, never the id. If the table leaks, the attacker cannot turn rows into cookies.
    3. **Check the expiry on every lookup.** `expires_at > now()` is part of the query, so an expired session simply does not exist.

    A plain SHA-256 is correct here, unlike for passwords. The token is 256 random bits, so there is nothing to guess and no point in a slow hash.

    <Callout type="security">
      HttpOnly stops a script from **reading** the cookie. It does not stop an XSS bug from **using** it by sending requests from inside the victim's page. HttpOnly limits the damage, it does not cure the bug.
    </Callout>
  </Step>
