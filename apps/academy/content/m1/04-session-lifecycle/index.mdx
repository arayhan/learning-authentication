<LessonSteps>
  <Step id="hook" title="Hook">
    A session is only as safe as the moments you create it, change it and destroy it. Most real session bugs are not in the cookie flags. They are in the timing.

    <Analogy title="New locks on move-in day">
      When you move into a flat you change the locks, because you cannot know who kept a copy of the old key. A session id is a key, and logging in is move-in day: the server should hand you a new one.
    </Analogy>
  </Step>

  <Step id="lifecycle" title="Birth to death">
    A session has a life, and each stage has a rule.

    | Stage | Rule |
    |---|---|
    | Create | After authentication, with a fresh random id |
    | Use | Look the id up on every request; check the expiry in the database |
    | Rotate | New id at login and at every privilege change: password change, MFA step-up, role change |
    | Expire | An **idle** timeout and an **absolute** timeout, enforced on the server |
    | Destroy | Logout deletes the server-side record, then clears the cookie |

    **Idle** timeout ends a session after a period without use. **Absolute** timeout ends it no matter what, so a stolen session cannot live forever. OWASP's Session Management cheat sheet suggests 2 to 5 minutes idle for high-value apps and 15 to 30 minutes for low-risk ones, and you pick the absolute limit from your risk.

    The lab keeps it small: one hour, absolute, stored in the database as `expires_at`. The cookie's `Max-Age` is only a hint to the browser. The server never trusts it.

    <Callout type="security">
      Changing a password should also **destroy every other session** of that user and give the current device a new one. If the reason for the change is "someone else had my password", their sessions must die too.
    </Callout>
  </Step>

  <Step id="rotation" title="Rotate on login">
    Here is the secure login, step by step. The server deletes whatever id the client arrived with, creates a new one, and sets it.

    <SequenceFlow flow={flows.sessionRotation} />

    Why bother? Because the id the browser held **before** login was created while nobody was authenticated, and nobody protected it. Anyone who knew it would be handed a logged-in session for free, if login simply kept it. Rotation closes that door.
  </Step>

  <Step id="session-fixation" title="Session fixation">
    **Session fixation** is the attack that rotation exists to stop. It turns the usual theft around: the attacker does not steal the victim's id, they **choose** it.

    1. The attacker obtains or invents a session id.
    2. They get it into the victim's browser. Real routes: a session id accepted from the URL, a cookie planted from a sibling subdomain or by an XSS bug, or a network attacker on plain HTTP.
    3. The victim logs in. A vulnerable server keeps the id and attaches the victim's account to it.
    4. The attacker sends requests with the id they always knew.

    <SequenceFlow flow={flows.fixation} />

    The fixes are simple and cheap:

    - **Always issue a new id at login** and delete the old one.
    - **Never accept a session id the server did not issue.**
    - Keep ids out of URLs, and use `Secure` and `HttpOnly` cookies.
  </Step>

    Log in, use the session, then log out and prove the session is really gone.

    <LabConsole

        { label: "Log out", method: "POST", path: "/logout", headers: { "X-CSRF-Token": "{{csrfToken}}" } },
        { label: "Whoami again", method: "GET", path: "/me" },
      ]}
    />

    Two things to notice:

    - **Log out** needs the CSRF token from your login response, because logging someone out is a state change too. The console fills it in from the last login. Without a token you would get `403`.
    - After logging out, **Whoami again** returns `401`. The server deleted the session, so even a copied cookie is dead.

    Try Log in twice in a row and watch the `sid` change in the Inspector's Cookies tab. That is rotation.
  </Step>
