<LessonSteps>
  <Step id="hook" title="Hook">
    Session cuma seaman momen saat kamu membuatnya, mengubahnya, dan menghancurkannya. Kebanyakan bug session di dunia nyata bukan di flag cookie. Bug-nya ada di timing.

    <Analogy title="Ganti kunci pas pindah kos">
      Pas pindah ke kos baru, kamu minta ganti kunci, karena nggak tahu siapa saja yang masih pegang duplikat kunci lama. Session id itu kunci, dan login adalah hari pindahan: server harus memberi kamu yang baru.
    </Analogy>
  </Step>

  <Step id="lifecycle" title="Dari lahir sampai mati">
    Session punya masa hidup, dan tiap tahap punya aturan.

    | Tahap | Aturan |
    |---|---|
    | Create | Setelah authentication, dengan id acak yang baru |
    | Use | Cari id di setiap request; cek expiry di database |
    | Rotate | Id baru saat login dan di setiap perubahan privilege: ganti password, MFA step-up, ganti role |
    | Expire | Timeout **idle** dan timeout **absolute**, ditegakkan di server |
    | Destroy | Logout menghapus catatan di sisi server, lalu membersihkan cookie |

    Timeout **idle** mengakhiri session setelah sekian lama tidak dipakai. Timeout **absolute** mengakhirinya apa pun yang terjadi, supaya session curian tidak hidup selamanya. Session Management cheat sheet OWASP menyarankan idle 2 sampai 5 menit untuk app bernilai tinggi dan 15 sampai 30 menit untuk yang berisiko rendah, dan batas absolute kamu tentukan dari risikonya.

    Lab ini dibuat sederhana: satu jam, absolute, disimpan di database sebagai `expires_at`. `Max-Age` di cookie hanya petunjuk untuk browser. Server tidak pernah mempercayainya.

    <Callout type="security">
      Ganti password juga harus **menghancurkan semua session lain** milik user itu dan memberi perangkat yang sedang dipakai session baru. Kalau alasan ganti password adalah "ada orang lain yang pegang passwordku", session mereka juga harus mati.
    </Callout>
  </Step>

  <Step id="rotation" title="Rotate saat login">
    Ini login yang aman, langkah demi langkah. Server menghapus id apa pun yang dibawa client, membuat yang baru, dan mengaturnya.

    <SequenceFlow flow={flows.sessionRotation} />

    Kenapa repot? Karena id yang dipegang browser **sebelum** login dibuat saat belum ada yang terautentikasi, dan tidak ada yang melindunginya. Siapa pun yang tahu id itu akan dapat session yang sudah login secara gratis, kalau login cuma mempertahankannya. Rotation menutup celah itu.
  </Step>

  <Step id="session-fixation" title="Session fixation">
    **Session fixation** adalah serangan yang ingin dihentikan oleh rotation. Ia membalik pencurian biasa: attacker tidak mencuri id korban, ia **memilihnya**.

    1. Attacker mendapatkan atau mengarang session id.
    2. Ia memasukkannya ke browser korban. Jalurnya nyata: session id yang diterima dari URL, cookie yang ditanam dari subdomain tetangga atau lewat bug XSS, atau attacker di jaringan lewat HTTP biasa.
    3. Korban login. Server yang rentan mempertahankan id itu dan menempelkan akun korban ke sana.
    4. Attacker mengirim request dengan id yang sudah ia tahu dari awal.

    <SequenceFlow flow={flows.fixation} />

    Perbaikannya sederhana dan murah:

    - **Selalu terbitkan id baru saat login** dan hapus yang lama.
    - **Jangan pernah menerima session id yang tidak diterbitkan server.**
    - Jauhkan id dari URL, dan pakai cookie `Secure` dan `HttpOnly`.
  </Step>

    Dua hal yang perlu diperhatikan:

    - **Log out** butuh CSRF token dari response login kamu, karena logout orang juga perubahan state. Console mengisinya dari login terakhir. Tanpa token kamu akan dapat `403`.
    - Setelah logout, **Whoami again** mengembalikan `401`. Server sudah menghapus session-nya, jadi cookie yang disalin pun sudah mati.

    Coba **Log in** dua kali berturut-turut dan lihat `sid` berubah di tab Cookies Inspector. Itulah rotation.
