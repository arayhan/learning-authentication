<LessonSteps>
  <Step id="hook" title="Hook">
    Modules 1 and 2 were about proving who a user is to **your own** service. Now a different app wants to work with that user's data at your service: a print shop that wants to fetch photos, a calendar tool that wants to read events.

    The oldest answer is to ask the user for their password. It works, and it is a disaster. This module is about the answer that replaced it.

    <Analogy title="The valet key">
      A valet key starts the car and opens the door, but not the trunk or the glove box. You hand it over without handing over your whole life. An access token is a valet key for your data.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    Picture a print shop asking for your photo-service password. Everything goes wrong at once:

    - **Too much power.** The shop can do anything you can: read private albums, delete photos, change your email.
    - **No way back.** The only way to cut the shop off is to change your password, which cuts off every other app you gave it to.
    - **A bigger target.** The shop now stores a password for another company's service. If the shop is breached, so are you.
    - **No second factor, no consent, no audit.** The photo service cannot tell the shop from you.

    **OAuth 2.0** (RFC 6749) fixes this with *delegated authorization*. The user signs in at the service that owns the data and approves a specific request. The app receives an **access token** that is limited in three ways:

    | Limit | What it means |
    |---|---|
    | **Scope** | Only the access that was approved, for example `photos.read` |
    | **Time** | It expires, in the lab after 5 minutes |
    | **Revocable** | The user or the service can withdraw it without touching the password |

    <SequenceFlow flow={flows.oauthRoles} />

    <Callout type="info">
      OAuth 2.0 answers "may this app do this?", not "who is this person?". The token says that an authority granted a client some access. Signing users in to an app is a separate job that **OpenID Connect** does on top of OAuth. Treating a plain access token as a login is a classic design mistake.
    </Callout>
  </Step>

  <Step id="roles" title="The four roles">
    RFC 6749 section 1.1 defines four roles. They are roles, not machines: one process can play several.

    | Role | Who it is | In the lab |
    |---|---|---|
    | **Resource owner** | The user who owns the data and can grant access | alice@example.com |
    | **Client** | The app that wants access on the user's behalf | `demo-spa`, a browser app on port 4113 (Go) or 4213 (TS) |
    | **Authorization server** | Authenticates the user, asks for consent, issues tokens | Port 4103 (Go) or 4203 (TS) |
    | **Resource server** | Hosts the data and accepts or rejects tokens | The photos API on port 4123 (Go) or 4223 (TS) |

    Three things to notice before you start building:

    1. **The client never sees the password.** The user types it at the authorization server only.
    2. **The resource server never talks to the user.** It reads the token the client sends. In the lab it checks the signature with the authorization server's public keys, exactly as you did in Module 2.
    3. **The token is the contract between the last two.** What is in it (`sub`, `client_id`, `scope`, `aud`, `exp`) is everything the API knows about the grant.

    In lessons 2 to 6 you will use all four. Watch the Inspector on the right: it shows requests from the authorization server and the API in one list, with a small badge for each role.

    <Callout type="info">
      In Phase 2 you will want to know which of these roles each of your own services plays. That is a good question to carry through the module.
    </Callout>
  </Step>
