<LessonSteps>
  <Step id="hook" title="Hook">
    Lesson 2 left one soft spot. The authorization code travels through the browser, and anything that can read that URL can get it. On a phone it is worse: the redirect goes to a custom URL scheme such as `com.example.bank:/callback`, and **any installed app can claim the same scheme**.

    If a stolen code can be redeemed by whoever holds it, the code is worth a token. PKCE (pronounced "pixy", RFC 7636) makes the code worthless to anyone but the app that asked for it.

    <Analogy title="The torn ticket">
      Tear a ticket in half and keep one half at home. Hand the other half to the clerk at the start. The clerk only gives you the prize when the two halves fit, so a thief with one half gets nothing.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    PKCE adds one secret and one commitment to the flow. Both are made fresh for every authorization request.

    1. The client creates a **`code_verifier`**: a random string of 43 to 128 characters from `A-Z a-z 0-9 - . _ ~`. Typically 32 random bytes, base64url encoded, which is 43 characters.
    2. It computes **`code_challenge = BASE64URL(SHA-256(code_verifier))`**, no padding. This is the `S256` method.
    3. `/authorize` gets the `code_challenge` and `code_challenge_method=S256`. The server stores the challenge with the code it issues.
    4. `/token` gets the `code_verifier`. The server hashes it and compares with the stored challenge, in constant time. Different means `invalid_grant`.

    <SequenceFlow flow={flows.authCodePkce} />

    The security comes from the direction of the hash. The challenge crosses the front channel, where an attacker can see it, but SHA-256 cannot be run backwards. The verifier crosses only the back channel, **after** the code was issued. An attacker who saw the redirect has the code and the challenge, and needs the verifier.

    Some rules that come straight from the RFCs:

    - **Use S256.** The `plain` method sends the verifier itself, which defeats the purpose. RFC 7636 only tolerates it for clients that cannot hash.
    - **A new verifier per request.** Never a constant, never derived from something an attacker can guess.
    - **The server must enforce it.** A server that accepts a missing challenge when the client could have sent one is open to a downgrade: the attacker strips the challenge from the request. The lab's secure `/authorize` rejects a request without a valid S256 challenge.
    - **Everyone should use it.** RFC 9700 requires PKCE for public clients and recommends it for confidential ones. OAuth 2.1 requires it for every client that uses the authorization code flow.

    <Callout type="info">
      PKCE was invented for mobile apps (RFC 7636 calls the attack the *authorization code interception attack*). It now also stops a code that was **injected** into a flow, and it is the reason the SPA flow is safe without a client secret.
    </Callout>
  </Step>

  <Step id="generator" title="Make a challenge">
    Compute one yourself. The generator takes a verifier, shows its bytes, the SHA-256 digest and the base64url result, and updates as you type. Click **Use the RFC 7636 example** and compare the result with Appendix B of the RFC: `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`.

    <PkceGenerator />

    Try editing a single character of the verifier. The challenge changes completely, and no partial change in the verifier gives a partial match. That is why a guess is useless.
  </Step>

  <Step id="lab" title="Lab">
    Make the server reject a verifier. In the generator above, click **Test a wrong verifier**. It posts a freshly invented verifier to the lab's `POST /token` and shows the answer: `400 invalid_grant`.

    <LabTasks />

    Open the `POST /token` row in the Inspector and look at the request body: `grant_type`, `client_id`, `code`, `redirect_uri`, `code_verifier`. The response body is `{"error":"invalid_grant"}`.

    By default the button sends a made-up code, so the server cannot tell you whether the code or the verifier was wrong, and it will not say. That is by design (RFC 6749 section 5.2 uses one error, `invalid_grant`, for a bad, expired, used or mismatched grant). To see the verifier mismatch alone, finish the *Break it* step first, copy a **PKCE** code from it, paste it into the generator and run the test again.
  </Step>

  <Step id="breakit" title="Break it">
    Now play the malicious app. The lab cannot run a second app on your phone, so the attack is staged with two browser tabs and the lab's attacker helper.

    <SequenceFlow flow={flows.codeInterception} />

    How the exercise works:

    1. **Flow A, no PKCE.** Click the first button. A tab opens at the lab's `/authorize` with `lab_mode=vulnerable` and no `code_challenge`: the vulnerable mode lets a request through without PKCE. Sign in as `alice@example.com` and approve. Your tab lands on the client at `/callback` and ignores the response, which is fine: **the code was never redeemed**. The component reads the code from the lab trace, the same URL a malicious app would have received.
    2. **Flow B, PKCE.** Do the same with the second button, which sends an S256 challenge.
    3. **Replay each code as the attacker.** The lab's `/__attack/intercept` helper does what the malicious app would do: it knows the code and the redirect URI it saw, but not the verifier, and it calls the token endpoint. The helper only exists in vulnerable mode.

      caption="The page each flow's new tab lands on. Sign in as alice@example.com, then approve."

    You are looking for `200` for Flow A and `400` for Flow B.

    <InterceptionAttack />

    Flow A produced an access token for alice, because a code issued without a challenge is a bearer secret. Flow B was **the same attack with the same capture**, and it failed. The attacker's failed attempt also did not burn the code: the real app could still redeem it with its verifier.

    <Callout type="security">
      PKCE does not stop the code from being stolen. It makes the stolen code useless. RFC 8252 adds the rest of the picture for mobile apps: prefer a claimed `https` link over a custom scheme, always use the system browser, and treat a custom scheme as shared.
    </Callout>
  </Step>
