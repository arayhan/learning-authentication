<LessonSteps>
  <Step id="hook" title="Hook">
    Lesson 2 meninggalkan satu titik lemah. Authorization code lewat browser, dan apa pun yang bisa membaca URL itu bisa mengambilnya. Di HP lebih parah: redirect menuju custom URL scheme seperti `com.example.bank:/callback`, dan **app apa pun yang terpasang bisa mengklaim scheme yang sama**.

    Kalau code curian bisa ditukar oleh siapa pun yang memegangnya, code itu bernilai sama dengan token. PKCE (dibaca "pixy", RFC 7636) membuat code nggak berharga bagi siapa pun kecuali app yang memintanya.

    <Analogy title="Tiket yang disobek dua">
      Sobek selembar tiket jadi dua dan simpan separuhnya di rumah. Serahkan separuh lainnya ke petugas di awal. Petugas hanya memberi hadiahnya kalau kedua sobekan itu pas, jadi pencuri yang cuma pegang satu sobekan nggak dapat apa-apa.
    </Analogy>
  </Step>

  <Step id="concept" title="Konsep">
    PKCE menambahkan satu secret dan satu komitmen ke flow. Keduanya dibuat baru di setiap authorization request.

    1. Client membuat **`code_verifier`**: string acak sepanjang 43 sampai 128 karakter dari `A-Z a-z 0-9 - . _ ~`. Biasanya 32 byte acak yang di-encode base64url, yaitu 43 karakter.
    2. Dia menghitung **`code_challenge = BASE64URL(SHA-256(code_verifier))`**, tanpa padding. Ini metode `S256`.
    3. `/authorize` menerima `code_challenge` dan `code_challenge_method=S256`. Server menyimpan challenge bersama code yang diterbitkannya.
    4. `/token` menerima `code_verifier`. Server meng-hash-nya dan membandingkan dengan challenge yang tersimpan, dalam constant time. Beda berarti `invalid_grant`.

    <SequenceFlow flow={flows.authCodePkce} />

    Keamanannya datang dari arah hash. Challenge melewati front channel, tempat attacker bisa melihatnya, tapi SHA-256 nggak bisa dijalankan mundur. Verifier hanya lewat back channel, **setelah** code diterbitkan. Attacker yang melihat redirect punya code dan challenge, dan masih butuh verifier.

    Beberapa aturan yang langsung dari RFC:

    - **Pakai S256.** Metode `plain` mengirim verifier itu sendiri, yang menggagalkan tujuannya. RFC 7636 hanya mentoleransinya untuk client yang nggak bisa melakukan hash.
    - **Verifier baru untuk setiap request.** Jangan pernah konstan, jangan pernah diturunkan dari sesuatu yang bisa ditebak attacker.
    - **Server harus menegakkannya.** Server yang menerima challenge kosong padahal client bisa mengirimnya rawan downgrade: attacker membuang challenge dari request. `/authorize` yang secure di lab menolak request tanpa S256 challenge yang valid.
    - **Semua client sebaiknya memakainya.** RFC 9700 mewajibkan PKCE untuk public client dan merekomendasikannya untuk confidential client. OAuth 2.1 mewajibkannya untuk setiap client yang memakai authorization code flow.

    <Callout type="info">
      PKCE awalnya dibuat untuk mobile app (RFC 7636 menyebut serangannya *authorization code interception attack*). Sekarang dia juga menghentikan code yang **disuntikkan** ke sebuah flow, dan dialah alasan flow SPA aman tanpa client secret.
    </Callout>
  </Step>

  <Step id="generator" title="Bikin challenge">
    Hitung sendiri satu challenge. Generator menerima verifier, menampilkan byte-nya, digest SHA-256, dan hasil base64url, dan ikut berubah saat kamu mengetik. Klik **Pakai contoh RFC 7636** dan bandingkan hasilnya dengan Appendix B di RFC: `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`.

    <PkceGenerator />

    Coba ubah satu karakter saja di verifier. Challenge berubah total, dan nggak ada perubahan sebagian pada verifier yang menghasilkan kecocokan sebagian. Itu sebabnya menebak itu percuma.
  </Step>

  <Step id="check" title="Cek">
    Tiga pertanyaan. Semua jawaban harus benar, tapi kamu boleh coba lagi sesering yang kamu mau.

    <Quiz id="q1" gate />
  </Step>

  <Step id="lab" title="Lab">
    Bikin server menolak sebuah verifier. Di generator di atas, klik **Tes verifier yang salah**. Dia mem-post verifier karangan baru ke `POST /token` milik lab dan menampilkan jawabannya: `400 invalid_grant`.

    <LabTasks />

    Buka baris `POST /token` di Inspector dan lihat body request-nya: `grant_type`, `client_id`, `code`, `redirect_uri`, `code_verifier`. Body response-nya `{"error":"invalid_grant"}`.

    Secara default tombol itu mengirim code karangan, jadi server nggak bisa bilang apakah code atau verifier yang salah, dan memang nggak akan bilang. Itu disengaja (RFC 6749 section 5.2 memakai satu error, `invalid_grant`, untuk grant yang buruk, kedaluwarsa, sudah dipakai, atau tidak cocok). Untuk melihat ketidakcocokan verifier saja, selesaikan dulu langkah *Break it*, salin code **PKCE** dari sana, tempel ke generator, dan jalankan tes lagi.
  </Step>

  <Step id="breakit" title="Break it">
    Sekarang berperan jadi app jahat. Lab nggak bisa menjalankan app kedua di HP-mu, jadi serangannya dipentaskan dengan dua tab browser dan attacker helper milik lab.

    <SequenceFlow flow={flows.codeInterception} />

    Cara kerja latihannya:

    1. **Flow A, tanpa PKCE.** Klik tombol pertama. Sebuah tab terbuka di `/authorize` milik lab dengan `lab_mode=vulnerable` dan tanpa `code_challenge`: vulnerable mode membiarkan request lolos tanpa PKCE. Login sebagai `alice@example.com` dan approve. Tab-mu mendarat di client pada `/callback` dan mengabaikan response, dan itu nggak masalah: **code-nya belum pernah ditukar**. Komponen membaca code dari trace lab, URL yang sama yang akan diterima app jahat.
    2. **Flow B, PKCE.** Lakukan hal yang sama dengan tombol kedua, yang mengirim S256 challenge.
    3. **Replay tiap code sebagai attacker.** Helper `/__attack/intercept` milik lab melakukan apa yang dilakukan app jahat: dia tahu code dan redirect URI yang dilihatnya, tapi nggak tahu verifier, lalu memanggil token endpoint. Helper itu hanya ada di vulnerable mode.

      caption="Halaman tujuan tab baru tiap flow. Login sebagai alice@example.com, lalu approve."

    Yang kamu cari: `200` untuk Flow A dan `400` untuk Flow B.

    <InterceptionAttack />

    Flow A menghasilkan access token untuk alice, karena code yang diterbitkan tanpa challenge itu bearer secret. Flow B adalah **serangan yang sama dengan hasil tangkapan yang sama**, dan gagal. Percobaan gagal attacker juga nggak menghanguskan code: app asli masih bisa menukarnya dengan verifier-nya.

    <Callout type="security">
      PKCE nggak mencegah code dicuri. Dia membuat code curian jadi nggak berguna. RFC 8252 melengkapi gambaran untuk mobile app: pilih link `https` yang diklaim ketimbang custom scheme, selalu pakai system browser, dan anggap custom scheme itu dipakai bersama.
    </Callout>
  </Step>
