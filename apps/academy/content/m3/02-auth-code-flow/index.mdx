<LessonSteps>
  <Step id="hook" title="Hook">
    User harus menyetujui app di authorization server, lalu app harus mendapat token. Bagian tricky-nya: gimana hasilnya balik ke app? Satu-satunya jalan antara keduanya adalah **browser**, dan browser itu tempat umum: URL masuk ke history, log, header `Referer`, dan extension.

    Authorization code flow menyelesaikannya dengan membagi pengiriman jadi dua. Browser membawa sesuatu yang nyaris nggak berharga, sedangkan bagian yang berharga lewat jalur privat.

    <Analogy title="Tiket penitipan tas">
      Di penitipan tas supermarket, kamu menyerahkan tas dan dapat nomor tiket. Tiket itu sendiri cuma secarik kertas, dan hanya petugas di konter yang bisa menukarnya dengan tasmu. Code itu tiketnya, dan token request itu konternya.
    </Analogy>
  </Step>

  <Step id="concept" title="Konsep">
    Flow ini punya dua channel. **Front channel** lewat browser user (redirect). **Back channel** adalah panggilan HTTPS langsung dari client ke authorization server.

    <SequenceFlow flow={flows.authCode} />

    **Langkah 1, authorization request** (front channel). Client mengarahkan browser ke `GET /authorize` dengan query parameter berikut (RFC 6749 section 4.1.1):

    | Parameter | Artinya |
    |---|---|
    | `response_type=code` | Pakai authorization code flow |
    | `client_id` | Client terdaftar mana yang meminta |
    | `redirect_uri` | Ke mana browser dikembalikan. Harus sama persis dengan nilai yang terdaftar |
    | `scope` | Akses yang diminta, dipisah spasi |
    | `state` | Nilai yang nggak bisa ditebak, dicek client saat kembali (lesson 5) |
    | `code_challenge`, `code_challenge_method` | PKCE (lesson 4). Wajib di lab |

    **Langkah 2, autentikasi dan consent.** Authorization server menampilkan halaman login-nya sendiri dan layar consent. Hanya di sini password itu ada.

    **Langkah 3, redirect balik** (front channel). Kalau disetujui, server menjawab `302` ke `redirect_uri` dengan `?code=...&state=...`. Kalau ditolak, dia mengirim `?error=access_denied`.

    **Langkah 4, token request** (back channel). Client memanggil `POST /token` dengan `grant_type=authorization_code`, `code`, `redirect_uri` yang sama, dan `client_id` (plus PKCE verifier). Jawabannya adalah access token.

    Code sengaja dibuat lemah kalau berdiri sendiri. Di lab, code itu:

    - **Umur pendek**: 60 detik.
    - **Sekali pakai**: dipakai kedua kali akan gagal, dan token dari penukaran pertama dicabut.
    - **Terikat** ke client dan `redirect_uri` persis yang dipakai saat code diterbitkan.
    - **Disimpan dalam bentuk hash**: database menyimpan sha256 dari code, seperti session id di Modul 1.

    <Callout type="security">
      Urutan pengecekan itu penting. RFC 6749 section 4.1.2.1 bilang `client_id` atau `redirect_uri` yang salah mendapat **halaman error tanpa redirect**, karena me-redirect ke URL yang belum diverifikasi menjadikan server sebagai open redirector. Hanya error yang datang setelahnya (`invalid_scope`, `access_denied`, `response_type` yang hilang) dilaporkan lewat redirect balik dengan `?error=...&state=...`.
    </Callout>

    Setiap token response membawa `Cache-Control: no-store` dan `Pragma: no-cache` (RFC 6749 section 5.1), alasannya sama seperti yang kamu lihat di Modul 2: token nggak boleh nangkring di cache.
  </Step>

    Lalu lihat apa yang direkam Inspector. Pilih barisnya satu per satu:

    - `GET /authorize` (role `as`): seluruh request ada di query string.
    - `POST /consent` (role `as`): sebuah `302` yang header **Location**-nya berisi `code`. Ini redirect yang diikuti browser.
    - `POST /token` (role `as`): code dan verifier masuk, access token keluar. Ini back channel.
    - `GET /api/photos` (role `api`): request membawa `Authorization: Bearer ...`.

    Dua request yang bisa kamu kirim manual di console di bawah. Yang pertama membuktikan client yang tidak dikenal mendapat halaman error tanpa redirect, dan yang kedua menampilkan public key yang dipakai API untuk memverifikasi token.
