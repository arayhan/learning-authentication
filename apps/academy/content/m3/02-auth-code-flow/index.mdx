<LessonSteps>
  <Step id="hook" title="Hook">
    The user has to approve the app at the authorization server, and then the app has to get a token. The tricky part is how the result gets back to the app, because the only road between the two is the **browser**, and the browser is a public place: URLs land in history, logs, `Referer` headers and extensions.

    The authorization code flow solves it by splitting the delivery in two. The browser carries something nearly worthless, and the valuable part travels on a private line.

    <Analogy title="The claim ticket">
      At a coat check you hand in your coat and get a paper ticket. The ticket alone is just paper, and only the counter can swap it for your coat. The code is the ticket, and the token request is the counter.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    The flow has two channels. The **front channel** goes through the user's browser (redirects). The **back channel** is a direct HTTPS call from the client to the authorization server.

    <SequenceFlow flow={flows.authCode} />

    **Step 1, the authorization request** (front channel). The client sends the browser to `GET /authorize` with these query parameters (RFC 6749 section 4.1.1):

    | Parameter | Meaning |
    |---|---|
    | `response_type=code` | Use the authorization code flow |
    | `client_id` | Which registered client is asking |
    | `redirect_uri` | Where to send the browser back. Must match a registered value exactly |
    | `scope` | The access requested, space separated |
    | `state` | An unguessable value the client checks on return (lesson 5) |
    | `code_challenge`, `code_challenge_method` | PKCE (lesson 4). Required by the lab |

    **Step 2, authentication and consent.** The authorization server shows its own sign-in page and a consent screen. Only here does the password exist.

    **Step 3, the redirect back** (front channel). On approval the server answers `302` to `redirect_uri` with `?code=...&state=...`. On refusal it sends `?error=access_denied`.

    **Step 4, the token request** (back channel). The client calls `POST /token` with `grant_type=authorization_code`, the `code`, the same `redirect_uri` and its `client_id` (plus the PKCE verifier). The answer is the access token.

    The code is deliberately weak on its own. In the lab it is:

    - **Short-lived**: 60 seconds.
    - **Single-use**: redeeming it a second time fails, and the tokens from the first redemption are revoked.
    - **Bound** to the client and the exact `redirect_uri` it was issued for.
    - **Stored hashed**: the database holds sha256 of the code, as with session ids in Module 1.

    <Callout type="security">
      The order of checks matters. RFC 6749 section 4.1.2.1 says that a bad `client_id` or `redirect_uri` gets an **error page and no redirect**, because redirecting to an unverified URL would make the server an open redirector. Only later errors (`invalid_scope`, `access_denied`, a missing `response_type`) are reported by redirecting back with `?error=...&state=...`.
    </Callout>

    Every token response carries `Cache-Control: no-store` and `Pragma: no-cache` (RFC 6749 section 5.1), for the same reason you saw in Module 2: a token must never sit in a cache.
  </Step>
