<LessonSteps>
  <Step id="hook" title="Hook">
    PKCE protects the code. Three smaller parameters decide how much damage anyone can do when something else goes wrong: **`scope`** limits what a token can do, **`state`** ties the response to the request, and **`redirect_uri`** decides who receives the code at all.

    Each one is a single line in a request, and each one is skipped or loosened in real systems because "it works without it".

    <Analogy title="The return address">
      A registered letter is only delivered to the address on file, and a "close enough" address gets it sent back. A redirect URI has to match the registered one to the character, because a near miss could be a mailbox the attacker owns.
    </Analogy>
  </Step>

  <Step id="concept" title="Scopes">
    A **scope** is a name for a unit of access. The client asks for scopes, the user approves them on the consent page, the token carries them, and the **resource server** enforces them. A scope that nobody checks is decoration.

    ```text
    scope=photos.read profile
    ```

    Scopes are space-separated (RFC 6749 section 3.3), so in a URL they are written with `%20`: `scope=photos.read%20profile`. The URL builder below encodes it that way.

    | Where | What happens to the scope |
    |---|---|
    | `/authorize` | Must be a subset of what this client may ever get. `demo-spa` can ask for `photos.read` and `profile`. Anything else gives `error=invalid_scope` |
    | Consent page | The user sees the scopes in plain language and approves or denies |
    | Token | The granted scope goes in the `scope` claim of the JWT and in the token response |
    | Resource server | The API reads the claim on every request and refuses what it does not cover |

    Two different failures are easy to confuse. The API answers per RFC 6750 section 3.1:

    - `401` with `WWW-Authenticate: Bearer error="invalid_token"`: the token itself is missing, expired, forged or revoked. Get a new one.
    - `403` with `WWW-Authenticate: Bearer error="insufficient_scope"`: the token is valid, but does not cover this request. A new token with more scope is needed, and the user may have to approve it.

    Least privilege applies as it does everywhere: ask for what the feature needs. A token that carries `photos.read` cannot be used to delete anything even if the app is compromised.
  </Step>

  <Step id="state" title="State">
    The redirect back to the client is a plain `GET` with a code in the query. The client cannot tell by looking whether it **asked** for this response. Without a check, an attacker can start a flow with their own account, stop before redeeming the code, and give the URL to a victim.

    <SequenceFlow flow={flows.stateCsrf} />

    The defense is the `state` parameter (RFC 6749 section 10.12):

    1. Before redirecting, the client creates an unguessable random value and ties it to **this browser session**, for example in memory or in sessionStorage.
    2. It sends it in `/authorize`. The authorization server returns it unchanged in the redirect, on success and on error.
    3. On the callback, the client compares the returned value with the stored one and discards the response on any mismatch, including a missing one.

    The lab's SPA does exactly this and shows the failure if you open a callback by hand: *Check the returned state, rejected*.

    <Callout type="info">
      RFC 9700 notes that PKCE also stops this attack when the client uses it correctly with a server that enforces it, because the attacker's code cannot be redeemed with the victim's verifier. `state` is still the common, simple guard, and it is also used to carry app state such as the page to return to. Do both.
    </Callout>
  </Step>

  <Step id="redirect" title="Redirect URIs">
    The `redirect_uri` is where the browser (and the code) is sent. It is the most attacked parameter in OAuth, because whoever receives the code is one step from a token.

    The rules (RFC 6749 section 3.1.2, RFC 9700 section 2.1, OAuth 2.1):

    - **Register ahead of time**, one entry per exact URI.
    - **Compare by exact string.** No prefix, no wildcard, no "starts with the registered host". `https://app.example/callback.evil` and `https://app.example/callback/../evil` are not `https://app.example/callback`.
    - **Never redirect on a bad value.** An unregistered `redirect_uri` or `client_id` gets an error page. Redirecting would make the server an open redirector.
    - **Use HTTPS** in production. The lab uses `http://localhost`, which RFC 8252 allows for loopback redirects.

    The vulnerable mode of the lab degrades the exact comparison into a **prefix match**, the real-world bug behind many "redirect URI bypass" reports. You will exploit it in *Break it*.
  </Step>

       ```bash
       curl -s -X POST http://localhost:4103/token \
         -d grant_type=authorization_code -d client_id=demo-spa -d code=CODE \
         -d redirect_uri=http://localhost:4113/callback
       ```

       The answer has `"scope":"profile"`. Copy the `access_token`.
    4. Call the API with it (replace `TOKEN`):

       ```bash
       curl -i http://localhost:4123/api/photos -H "Authorization: Bearer TOKEN"
       ```

       The answer is `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="photos.read"`. The token is genuine and unexpired. It just does not cover photos.

    The code lives only 60 seconds, so do steps 2 and 3 straight away.

  <Step id="breakit" title="Break it">
    The redirect prefix attack. The attacker asks for a `redirect_uri` that **starts with** the registered one: `.../callback.evil`. The same request goes to the secure server and to the vulnerable one.

    <OAuthUrlBuilder attack />

    You are looking for `400` on the secure side and `200` on the vulnerable side. A `200` there means the server accepted the evil URI and showed its sign-in page. If a user approved, the code would be sent to `callback.evil`, a URL the attacker controls, and PKCE would be the only thing left between them and a token.

    To see it through, set the redirect to the `.evil` one, tick **Vulnerable mode**, and open the URL: the final redirect lands on a page that does not exist, with the code visible in the address bar. In a real attack that page is the attacker's.

    <Callout type="security">
      The defense is one line: compare the strings. Do not parse the URI and compare only the host, do not allow a wildcard, and do not treat a registered URI as a prefix. Add a path or query by registering that exact URI.
    </Callout>
  </Step>
