<LessonSteps>
  <Step id="hook" title="Hook">
    PKCE melindungi code. Tiga parameter yang lebih kecil menentukan seberapa besar kerusakan yang bisa terjadi kalau ada hal lain yang salah: **`scope`** membatasi apa yang bisa dilakukan token, **`state`** mengikat response ke request, dan **`redirect_uri`** menentukan siapa yang menerima code.

    Masing-masing cuma satu baris di request, dan masing-masing sering dilewati atau dilonggarkan di sistem nyata karena "toh jalan tanpa itu".

    <Analogy title="Alamat paket">
      Paket dari kurir hanya diantar ke alamat yang terdaftar, dan alamat yang "mirip-mirip" dikembalikan ke pengirim. Redirect URI harus sama persis dengan yang terdaftar sampai ke karakter terakhir, karena yang cuma mirip bisa jadi kotak surat milik attacker.
    </Analogy>
  </Step>

  <Step id="concept" title="Scope">
    **Scope** adalah nama untuk satu unit akses. Client meminta scope, user menyetujuinya di halaman consent, token membawanya, dan **resource server** menegakkannya. Scope yang nggak dicek siapa pun cuma hiasan.

    ```text
    scope=photos.read profile
    ```

    Scope dipisah spasi (RFC 6749 section 3.3), jadi di URL ditulis dengan `%20`: `scope=photos.read%20profile`. URL builder di bawah meng-encode-nya begitu.

    | Di mana | Apa yang terjadi pada scope |
    |---|---|
    | `/authorize` | Harus subset dari yang boleh didapat client ini. `demo-spa` bisa meminta `photos.read` dan `profile`. Selain itu menghasilkan `error=invalid_scope` |
    | Halaman consent | User melihat scope dalam bahasa biasa lalu menyetujui atau menolak |
    | Token | Scope yang diberikan masuk ke claim `scope` di JWT dan ke token response |
    | Resource server | API membaca claim itu di setiap request dan menolak yang nggak tercakup |

    Dua kegagalan yang berbeda gampang tertukar. API menjawab sesuai RFC 6750 section 3.1:

    - `401` dengan `WWW-Authenticate: Bearer error="invalid_token"`: token-nya sendiri hilang, kedaluwarsa, dipalsukan, atau dicabut. Minta yang baru.
    - `403` dengan `WWW-Authenticate: Bearer error="insufficient_scope"`: token valid, tapi nggak mencakup request ini. Butuh token baru dengan scope lebih banyak, dan user mungkin harus menyetujuinya.

    Least privilege berlaku seperti di mana-mana: minta apa yang dibutuhkan fitur itu. Token yang membawa `photos.read` nggak bisa dipakai menghapus apa pun, bahkan kalau app-nya dikompromikan.
  </Step>

  <Step id="state" title="State">
    Redirect balik ke client adalah `GET` biasa dengan code di query. Client nggak bisa tahu cuma dengan melihat apakah dia **memang meminta** response ini. Tanpa pengecekan, attacker bisa memulai flow dengan akunnya sendiri, berhenti sebelum menukar code, lalu memberikan URL-nya ke korban.

    <SequenceFlow flow={flows.stateCsrf} />

    Pertahanannya adalah parameter `state` (RFC 6749 section 10.12):

    1. Sebelum redirect, client membuat nilai acak yang nggak bisa ditebak dan mengikatnya ke **session browser ini**, misalnya di memory atau sessionStorage.
    2. Dia mengirimnya di `/authorize`. Authorization server mengembalikannya tanpa berubah di redirect, baik saat sukses maupun error.
    3. Di callback, client membandingkan nilai yang kembali dengan yang tersimpan dan membuang response kalau ada ketidakcocokan, termasuk kalau nilainya hilang.

    SPA di lab melakukan persis ini dan menampilkan kegagalannya kalau kamu membuka callback secara manual: *Check the returned state, rejected*.

    <Callout type="info">
      RFC 9700 mencatat bahwa PKCE juga menghentikan serangan ini kalau client memakainya dengan benar bersama server yang menegakkannya, karena code milik attacker nggak bisa ditukar dengan verifier milik korban. `state` tetap pengaman yang umum dan sederhana, dan juga dipakai untuk membawa state app seperti halaman tujuan setelah login. Pakai keduanya.
    </Callout>
  </Step>

  <Step id="redirect" title="Redirect URI">
    `redirect_uri` adalah tujuan browser (dan code) dikirim. Dia parameter yang paling sering diserang di OAuth, karena siapa pun yang menerima code tinggal selangkah dari token.

    Aturannya (RFC 6749 section 3.1.2, RFC 9700 section 2.1, OAuth 2.1):

    - **Daftarkan di awal**, satu entri per URI yang persis.
    - **Bandingkan dengan exact string.** Bukan prefix, bukan wildcard, bukan "diawali host yang terdaftar". `https://app.example/callback.evil` dan `https://app.example/callback/../evil` bukan `https://app.example/callback`.
    - **Jangan pernah redirect untuk nilai yang salah.** `redirect_uri` atau `client_id` yang tidak terdaftar mendapat halaman error. Me-redirect menjadikan server open redirector.
    - **Pakai HTTPS** di production. Lab memakai `http://localhost`, yang diizinkan RFC 8252 untuk redirect loopback.

    Vulnerable mode di lab menurunkan perbandingan persis menjadi **prefix match**, bug nyata di balik banyak laporan "redirect URI bypass". Kamu akan mengeksploitasinya di *Break it*.
  </Step>

  <Step id="lab" title="Lab">
    Builder menyusun URL `/authorize` dari field-fieldnya, meng-encode tiap nilai, dan menjelaskan tiap parameter. **Buka di tab baru** meluncurkannya ke implementasi yang kamu pilih.

    <LabTasks />

    <OAuthUrlBuilder />

    **Task 1, 400 dari pengecekan redirect.** Klik **Use the .evil redirect**, biarkan vulnerable mode tidak dicentang, lalu klik **Buka di tab baru**. Kamu mendapat halaman error, bukan halaman login: server menolak mempercayai redirect URI itu. Inspector menampilkan `GET /authorize` dengan `400`.

    **Task 2, token valid yang kekurangan scope.** Ini butuh token yang scope-nya hanya `profile`. Browser akan menelan code-nya, jadi baca dari Inspector dan selesaikan dengan `curl`. Pakai port implementasi yang kamu pilih (`4103`/`4123` untuk Go, `4203`/`4223` untuk TypeScript).

    1. Di builder klik **Reset redirect**, ubah `scope` jadi `profile`, **kosongkan** kotak `code_challenge`, dan centang **Vulnerable mode** (itu melewati PKCE supaya `curl` tetap pendek; pelajaran scope nggak bergantung padanya). Buka URL-nya, login, dan approve. Tab akan menampilkan app client menolak response yang tidak diminta. Itu memang diharapkan.
    2. Di Inspector pilih `POST /consent` dan salin `code` dari header **Location**.
    3. Tukar (ganti `CODE`):

       ```bash
       curl -s -X POST http://localhost:4103/token \
         -d grant_type=authorization_code -d client_id=demo-spa -d code=CODE \
         -d redirect_uri=http://localhost:4113/callback
       ```

       Jawabannya berisi `"scope":"profile"`. Salin `access_token`.
    4. Panggil API dengannya (ganti `TOKEN`):

       ```bash
       curl -i http://localhost:4123/api/photos -H "Authorization: Bearer TOKEN"
       ```

       Jawabannya `403` dengan `WWW-Authenticate: Bearer error="insufficient_scope", scope="photos.read"`. Token-nya asli dan belum kedaluwarsa. Dia cuma nggak mencakup foto.

    Code hanya hidup 60 detik, jadi lakukan langkah 2 dan 3 langsung.
  </Step>

  <Step id="breakit" title="Break it">
    Redirect prefix attack. Attacker meminta `redirect_uri` yang **diawali** dengan yang terdaftar: `.../callback.evil`. Request yang sama dikirim ke secure server dan ke vulnerable server.

    <OAuthUrlBuilder attack />

    Yang kamu cari: `400` di sisi secure dan `200` di sisi vulnerable. `200` di sana berarti server menerima URI jahat itu dan menampilkan halaman login-nya. Kalau user approve, code akan dikirim ke `callback.evil`, URL yang dikendalikan attacker, dan PKCE jadi satu-satunya yang tersisa antara mereka dan sebuah token.

    Untuk melihatnya sampai tuntas, set redirect ke yang `.evil`, centang **Vulnerable mode**, dan buka URL-nya: redirect terakhir mendarat di halaman yang nggak ada, dengan code terlihat di address bar. Di serangan nyata, halaman itu milik attacker.

    <Callout type="security">
      Pertahanannya satu baris: bandingkan string-nya. Jangan mem-parse URI lalu membandingkan host saja, jangan izinkan wildcard, dan jangan perlakukan URI terdaftar sebagai prefix. Mau menambah path atau query? Daftarkan URI persis itu.
    </Callout>
  </Step>
