<LessonSteps>
  <Step id="hook" title="Hook">
    Everything so far had a human in the loop: someone to sign in, someone to click Approve. But a nightly report job, a billing service or a build pipeline has no human and no browser. It still has to call an API, and the API still wants a token.

    For that case OAuth has a much shorter flow, with one request and no redirects.

    <Analogy title="The company badge">
      A delivery robot at an office has no name or face, so it carries a company badge that opens exactly the doors it is allowed to. The guard checks the badge, not a person. Client credentials is the badge.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    The **client credentials grant** (RFC 6749 section 4.4) lets a confidential client get an access token **for itself**. There is no resource owner, no consent page and no authorization code.

    <SequenceFlow flow={flows.clientCredentials} />

    The client sends `POST /token` with `grant_type=client_credentials`, an optional `scope`, and authenticates itself. The most common way is HTTP Basic, with the client id and secret joined by a colon and base64 encoded (RFC 6749 section 2.3.1). The answer is an access token and no refresh token.

    Points worth remembering:

    - **The subject is the client.** The token's `sub` is `demo-backend`, not a user. An API must not treat such a token as a user's.
    - **The scope is capped by registration.** The client may ask for less than it is allowed, never more: `scope=profile` for `demo-backend` gives `invalid_scope`.
    - **No refresh token.** The client can authenticate again whenever it needs a token, so a long-lived refresh token would add risk and no benefit.
    - **Wrong secret: `401 invalid_client`**, with a `WWW-Authenticate: Basic` header (RFC 6749 section 5.2).
    - **Only for confidential clients.** The secret must stay on a server. Browser and mobile apps cannot use this grant.

    How the two main grants compare:

    | | **Authorization code + PKCE** | **Client credentials** |
    |---|---|---|
    | A user is involved | Yes, signs in and consents | No |
    | Browser and redirects | Yes | None |
    | Token is about | The user, granted to the client | The client itself |
    | Client authentication | Public: PKCE. Confidential: secret too | Secret or key, always |
    | Refresh token | Possible | Not issued |
    | Typical use | A user's app acting for them | Service to service, jobs, automation |

    <Callout type="warn">
      A shared secret is a password for a program. Keep it in a secrets manager, never in the repository or an image, give each service its own, and rotate it. Stronger client authentication exists, such as signed JWT assertions or mutual TLS (RFC 7523, RFC 8705), and removes the shared secret altogether.
    </Callout>
  </Step>

  <Step id="lab" title="Lab">
    Be the backend job. The console below calls `POST /token` as `demo-backend` (secret `lab-secret`), using HTTP Basic.

    <LabTasks />

    <LabConsole
      lab="03"
      actions={[
        {
          label: "Get a token",
          method: "POST",
          path: "/token",
          headers: { "Content-Type": "application/x-www-form-urlencoded", Authorization: "Basic ZGVtby1iYWNrZW5kOmxhYi1zZWNyZXQ=" },
          body: "grant_type=client_credentials&scope=photos.read",
        },
        {
          label: "Wrong secret",
          method: "POST",
          path: "/token",
          headers: { "Content-Type": "application/x-www-form-urlencoded", Authorization: "Basic ZGVtby1iYWNrZW5kOm5vcGU=" },
          body: "grant_type=client_credentials",
        },
        {
          label: "Ask for a scope it lacks",
          method: "POST",
          path: "/token",
          headers: { "Content-Type": "application/x-www-form-urlencoded", Authorization: "Basic ZGVtby1iYWNrZW5kOmxhYi1zZWNyZXQ=" },
          body: "grant_type=client_credentials&scope=profile",
        },
      ]}
    />

    1. Click **Get a token**. The answer is `200` with `access_token`, `token_type`, `expires_in` and `scope`: `photos.read`. There is no `refresh_token`.
    2. Click **Wrong secret**. You get `401` with `invalid_client` and a `WWW-Authenticate: Basic` header.
    3. Click **Ask for a scope it lacks**. You get `400 invalid_scope`: `profile` is not among `demo-backend`'s registered scopes.
    4. Decode the token from step 1 the way you did in Module 2 (it is base64url JSON in the middle segment). Both `sub` and `client_id` are `demo-backend`.

    Then use it. The API is on a different port, so copy the `access_token` from the console and call it with `curl` (port `4123` for Go, `4223` for TypeScript):

    ```bash
    curl -i http://localhost:4123/api/photos -H "Authorization: Bearer TOKEN"
    ```

    The API treated it like any other valid token: it checked the signature, issuer, audience and expiry, saw `photos.read`, and answered `200`. It never needed to know that no user was involved.
