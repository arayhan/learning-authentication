<LessonSteps>
  <Step id="hook" title="Hook">
    In lesson 2 the client sent a code to `/token` and got a token back. A question was hiding in that step: how does the authorization server know the request really comes from the client it says it is?

    The answer depends on what kind of program the client is. A server in a locked room can keep a password. An app that you download to a stranger's device cannot.

    <Analogy title="The diary">
      A diary kept in a locked drawer stays private, and a diary left open on a shared table does not. Code that runs on the user's device is the table: whatever you write in it, the user and anyone near them can read.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    RFC 6749 section 2.1 sorts clients by one question: **can this client keep a credential confidential?**

    | | **Confidential client** | **Public client** |
    |---|---|---|
    | Can keep a secret | Yes | No |
    | Examples | Server-rendered web app, backend service, a job | Single-page app, mobile app, desktop app |
    | Authenticates at `/token` | With its secret or a key | It cannot, so it only sends its `client_id` |
    | What protects its codes | The secret, and PKCE (recommended) | PKCE (required) |
    | In the lab | `demo-backend` has the secret `lab-secret` | `demo-spa` has no secret |

    The lab registers both. The point of the table is the last row. A public client's `client_id` is not a secret, its redirect URI is in its own source, and its token request can be copied by anyone. If an attacker steals a code, nothing but PKCE stops them from redeeming it.

    <Callout type="warn">
      Do not make a SPA "confidential" by embedding a `client_secret` in its bundle. Everyone who loads the page has the secret, so it proves nothing, and it can give a false sense of safety. Treat browser and mobile apps as public clients.
    </Callout>

    A common alternative for browser apps is a **backend for frontend**: a small server that holds the tokens and the client secret, and talks to the browser with an ordinary session cookie. The browser then never sees an OAuth token. It trades the token handling problems of Module 2, lesson 4, for a stateful server.

    **Native apps** (phones, desktops) are public clients too. RFC 8252 asks them to sign in through the **system browser**, never an embedded web view, so the app cannot read the user's password. Lesson 4 shows what goes wrong with the redirect on a phone.
  </Step>

  <Step id="implicit" title="The implicit flow">
    Before PKCE existed, browser apps used the **implicit flow** (RFC 6749 section 4.2): no code, no back channel. The authorization server returned the access token directly, in the URL fragment of the redirect. It was designed for the case "the browser cannot make a cross-origin request", which stopped being true once CORS arrived.

    <SequenceFlow flow={flows.implicitDeprecated} />

    Why it was retired (RFC 9700 and OAuth 2.1):

    - **The token is in the URL.** It reaches browser history, extensions, scripts, shared screens and anything else that sees the address bar.
    - **No binding.** Any party that gets the token can use it. There is no step where the client proves it is the one that asked.
    - **No refresh tokens and no client authentication.** The flow has no back-channel step where either could happen.

    The replacement is not a new flow. It is the one from lesson 2 with PKCE, which works for the same apps and keeps the token off the URL. You can ask the lab for the old flow and see it refuse (use the port of your selected implementation):

    ```bash
    curl -i "http://localhost:4103/authorize?response_type=token&client_id=demo-spa&redirect_uri=http%3A%2F%2Flocalhost%3A4113%2Fcallback&scope=photos.read&state=abc"
    ```

    The answer is `302` to the callback with `error=unsupported_response_type`. The same reasoning removes the **resource owner password credentials** grant, where the app collects the password itself, which defeats the purpose of this whole module.
  </Step>
