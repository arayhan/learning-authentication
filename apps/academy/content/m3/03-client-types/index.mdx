<LessonSteps>
  <Step id="hook" title="Hook">
    Di lesson 2, client mengirim code ke `/token` dan dapat token. Ada satu pertanyaan yang tersembunyi di langkah itu: gimana authorization server tahu request itu benar-benar datang dari client yang diklaimnya?

    Jawabannya tergantung jenis program si client. Server di ruangan terkunci bisa menyimpan password. App yang di-download ke perangkat orang asing nggak bisa.

    <Analogy title="Buku diary">
      Diary yang disimpan di laci terkunci tetap privat, sedangkan diary yang dibiarkan terbuka di meja kantin nggak. Kode yang jalan di perangkat user itu mejanya: apa pun yang kamu tulis di situ bisa dibaca user dan siapa saja di dekatnya.
    </Analogy>
  </Step>

  <Step id="concept" title="Konsep">
    RFC 6749 section 2.1 mengelompokkan client dengan satu pertanyaan: **bisakah client ini menjaga credential tetap rahasia?**

    | | **Confidential client** | **Public client** |
    |---|---|---|
    | Bisa menyimpan secret | Ya | Tidak |
    | Contoh | Web app server-rendered, backend service, sebuah job | Single-page app, mobile app, desktop app |
    | Autentikasi di `/token` | Dengan secret atau key | Nggak bisa, jadi hanya mengirim `client_id` |
    | Yang melindungi code-nya | Secret, dan PKCE (direkomendasikan) | PKCE (wajib) |
    | Di lab | `demo-backend` punya secret `lab-secret` | `demo-spa` tanpa secret |

    Lab mendaftarkan keduanya. Poin tabel ini ada di baris terakhir. `client_id` milik public client bukan rahasia, redirect URI-nya ada di source-nya sendiri, dan token request-nya bisa disalin siapa saja. Kalau attacker mencuri code, hanya PKCE yang mencegahnya menukar code itu.

    <Callout type="warn">
      Jangan menjadikan SPA "confidential" dengan menanam `client_secret` di bundle-nya. Semua orang yang membuka halaman punya secret itu, jadi dia nggak membuktikan apa-apa dan malah memberi rasa aman palsu. Perlakukan app browser dan mobile sebagai public client.
    </Callout>

    Alternatif umum untuk app browser adalah **backend for frontend**: server kecil yang memegang token dan client secret, lalu bicara ke browser lewat session cookie biasa. Browser jadi nggak pernah melihat OAuth token. Tukarannya: masalah penanganan token di Modul 2, lesson 4, diganti dengan server yang stateful.

    **Native app** (HP, desktop) juga public client. RFC 8252 meminta mereka login lewat **system browser**, bukan embedded web view, supaya app nggak bisa membaca password user. Lesson 4 menunjukkan apa yang bisa salah dengan redirect di HP.
  </Step>

  <Step id="implicit" title="Implicit flow">
    Sebelum PKCE ada, app browser memakai **implicit flow** (RFC 6749 section 4.2): tanpa code, tanpa back channel. Authorization server mengembalikan access token langsung di URL fragment pada redirect. Dibuat untuk kasus "browser nggak bisa membuat cross-origin request", yang sudah nggak benar sejak CORS hadir.

    <SequenceFlow flow={flows.implicitDeprecated} />

    Kenapa dipensiunkan (RFC 9700 dan OAuth 2.1):

    - **Token ada di URL.** Dia masuk ke history browser, extension, script, layar yang di-share, dan apa pun yang bisa melihat address bar.
    - **Nggak ada binding.** Pihak mana pun yang mendapat token bisa memakainya. Nggak ada langkah di mana client membuktikan dirinya yang tadi meminta.
    - **Nggak ada refresh token dan client authentication.** Flow ini nggak punya langkah back channel tempat keduanya bisa terjadi.

    Penggantinya bukan flow baru. Penggantinya flow dari lesson 2 dengan PKCE, yang cocok untuk app yang sama dan menjaga token tetap di luar URL. Kamu bisa meminta flow lama ke lab dan melihat dia menolak (pakai port implementasi yang kamu pilih):

    ```bash
    curl -i "http://localhost:4103/authorize?response_type=token&client_id=demo-spa&redirect_uri=http%3A%2F%2Flocalhost%3A4113%2Fcallback&scope=photos.read&state=abc"
    ```

    Jawabannya `302` ke callback dengan `error=unsupported_response_type`. Alasan yang sama juga menghapus grant **resource owner password credentials**, di mana app mengumpulkan password sendiri, yang menggagalkan tujuan seluruh modul ini.
  </Step>
