<LessonSteps>
  <Step id="hook" title="Hook">
    In Module 1 the server remembered you: a cookie pointed at a row in a table. Now imagine the server remembers nothing, and you simply hand it a small signed note that says who you are. Any server that trusts the signer can read the note and believe it.

    That note is a **JSON Web Token (JWT)**, and it is everywhere: API calls, single sign-on, mobile apps. It is also misunderstood more often than almost anything in authentication.

    <Analogy title="The concert wristband">
      Anyone can look at your wristband and read the date and the zone printed on it. Nobody can make a new one, because the print is hard to copy. The guard never phones the box office: the wristband itself is the proof.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    A JWT is three pieces of text joined by dots: **header.payload.signature**. This is the compact form of a JSON Web Signature (JWS, RFC 7515), and the claims format is defined in RFC 7519.

    | Part | What it holds | Example from the lab |
    |---|---|---|
    | **Header** | How the token was signed | `{"alg":"RS256","typ":"JWT","kid":"k3Hq9ZmB1vW8eYrT"}` |
    | **Payload** | The **claims**: statements about the user and the token | `{"iss":"http://localhost:4102","sub":"6f1c…","exp":1767225900,…}` |
    | **Signature** | A signature over `base64url(header) + "." + base64url(payload)` | 256 bytes for RS256 |

    Header and payload are JSON, encoded with **base64url**. That is an encoding, not encryption: anyone holding the token can read both. The signature is what makes the token trustworthy. Change one byte of the payload and the signature no longer matches.

    <SequenceFlow flow={flows.statefulVsStateless} />

    Two properties follow, and every lesson in this module builds on them.

    1. **Self-contained.** The API verifies the token with a key and reads the claims from the token itself. There is no session lookup.
    2. **Bearer.** Whoever holds the token is treated as the user. The signature proves who *issued* it, not who is *presenting* it.

    <Callout type="security">
      A signed JWT is **readable by everyone who holds it**. Never put passwords, secrets or sensitive personal data in the payload. If you need confidentiality, use an encrypted token (JWE) or keep the data on the server and put only an id in the token.
    </Callout>
  </Step>

  <Step id="claims" title="Claims">
    The payload is a set of claims. A few names are **registered** (RFC 7519 section 4.1), and a verifier is expected to understand them.

    | Claim | Meaning | A verifier must |
    |---|---|---|
    | `iss` | **Issuer**: who made the token | Check it equals the issuer it trusts |
    | `sub` | **Subject**: who the token is about | Use it as the user id |
    | `aud` | **Audience**: which API it is for | Reject it if the API is not listed |
    | `exp` | **Expiration** time, in Unix seconds | Reject it after this moment |
    | `iat` | **Issued at** | Treat it as information |
    | `nbf` | **Not before** | Reject it before this moment |
    | `jti` | **JWT ID**, unique per token | Use it for logging or a deny list |

    The header has its own important field: **`kid`** (key id), which says which of the issuer's keys signed the token. Lesson 2 uses it. **`alg`** names the signature algorithm. It is attacker-controlled input, and lesson 5 shows what happens when a verifier believes it.

    Lab 02 adds one custom claim, `email`. Custom claims are fine, but remember the token is readable and cannot be taken back: keep them few and non-sensitive.

    <Callout type="warn">
      The lab puts `exp` five minutes after `iat`. Lifetimes are a security setting, not a convenience. Because a self-contained token cannot be recalled, a short life is the main thing that limits what a stolen token is worth.
    </Callout>
  </Step>

  <Step id="tradeoff" title="Sessions or tokens?">
    Neither one is simply better. They move the state to a different place.

    | | Server session (Module 1) | JWT access token |
    |---|---|---|
    | Where the truth lives | A row in the server's session table | Inside the signed token |
    | Check on each request | Look up the session | Verify the signature and claims |
    | Revoke at once | Yes, delete the row | Not until `exp` (lesson 6) |
    | Several services | They must share the session store | Each needs only the public key |
    | Size on the wire | A short random id | Hundreds of bytes, sent on every request |
    | Stale data | Always current | Claims are frozen at issue time |

    JWTs make the most sense when **more than one service** has to trust the same login, as with an identity provider and several APIs, or when you want verification with no shared database. For a single web app talking to its own backend, a plain server session is often simpler and safer.

    <Callout type="info">
      Worth asking of your own system: when **sso-backend** issues a token that **core-api** accepts, which claims does core-api actually check, and is that the same list as the table above?
    </Callout>
  </Step>
