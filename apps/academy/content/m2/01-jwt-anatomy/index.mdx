<LessonSteps>
  <Step id="hook" title="Pembuka">
    Di Module 1, server yang **mengingat** kamu: cookie menunjuk ke satu baris di tabel. Sekarang bayangkan server nggak mengingat apa-apa, dan kamu cukup menyodorkan secarik catatan bertanda tangan yang bilang kamu siapa. Server mana pun yang percaya sama penandatangannya bisa baca catatan itu dan langsung percaya.

    Catatan itu namanya **JSON Web Token (JWT)**, dan dia ada di mana-mana: API call, single sign-on, aplikasi mobile. Dia juga salah satu hal yang paling sering disalahpahami di dunia authentication.

    <Analogy title="Gelang tiket konser">
      Siapa pun bisa melirik gelang kamu dan membaca tanggal serta zona yang tercetak di situ. Tapi nggak ada yang bisa bikin gelang baru, karena cetakannya susah ditiru. Petugas gate nggak perlu telepon box office: gelangnya sendiri sudah jadi buktinya.
    </Analogy>
  </Step>

  <Step id="concept" title="Konsep">
    JWT itu tiga potong teks yang disambung titik: **header.payload.signature**. Ini bentuk compact dari JSON Web Signature (JWS, RFC 7515), sedangkan format claims-nya didefinisikan di RFC 7519.

    | Bagian | Isinya | Contoh dari lab |
    |---|---|---|
    | **Header** | Cara token ini di-sign | `{"alg":"RS256","typ":"JWT","kid":"k3Hq9ZmB1vW8eYrT"}` |
    | **Payload** | **Claims**: pernyataan soal user dan token | `{"iss":"http://localhost:4102","sub":"6f1c…","exp":1767225900,…}` |
    | **Signature** | Signature atas `base64url(header) + "." + base64url(payload)` | 256 byte untuk RS256 |

    Header dan payload itu JSON yang di-encode pakai **base64url**. Itu encoding, bukan enkripsi: siapa pun yang pegang token bisa membaca keduanya. Yang bikin token bisa dipercaya adalah signature-nya. Ubah satu byte saja di payload, signature langsung nggak cocok.

    <SequenceFlow flow={flows.statefulVsStateless} />

    Dari sini muncul dua sifat, dan setiap lesson di module ini dibangun di atasnya.

    1. **Self-contained.** API memverifikasi token pakai key dan membaca claims langsung dari token. Nggak ada lookup session.
    2. **Bearer.** Siapa pun yang memegang token dianggap sebagai user-nya. Signature membuktikan siapa yang *menerbitkan*, bukan siapa yang *menyodorkan*.

    <Callout type="security">
      JWT yang di-sign **bisa dibaca semua orang yang memegangnya**. Jangan pernah taruh password, secret, atau data pribadi yang sensitif di payload. Kalau butuh kerahasiaan, pakai token terenkripsi (JWE) atau simpan datanya di server dan taruh id-nya saja di token.
    </Callout>
  </Step>

  <Step id="claims" title="Claims">
    Payload itu kumpulan claims. Beberapa nama bersifat **registered** (RFC 7519 section 4.1), dan verifier diharapkan paham maknanya.

    | Claim | Arti | Yang harus dilakukan verifier |
    |---|---|---|
    | `iss` | **Issuer**: siapa yang membuat token | Cek sama dengan issuer yang dipercaya |
    | `sub` | **Subject**: token ini tentang siapa | Pakai sebagai user id |
    | `aud` | **Audience**: token ini untuk API mana | Tolak kalau API-nya nggak tercantum |
    | `exp` | Waktu **expiration**, dalam detik Unix | Tolak setelah saat ini |
    | `iat` | **Issued at**: kapan diterbitkan | Anggap sebagai informasi |
    | `nbf` | **Not before**: baru berlaku setelah | Tolak sebelum saat ini |
    | `jti` | **JWT ID**, unik per token | Pakai untuk logging atau deny list |

    Header juga punya field penting sendiri: **`kid`** (key id), yang menunjukkan key mana dari issuer yang dipakai men-sign token. Lesson 2 memakainya. **`alg`** menyebut algoritma signature. Ini input yang dikontrol attacker, dan lesson 5 menunjukkan apa yang terjadi kalau verifier percaya begitu saja.

    Lab 02 menambahkan satu custom claim, `email`. Custom claim boleh-boleh saja, tapi ingat token itu bisa dibaca dan nggak bisa ditarik kembali: jumlahnya sedikit saja dan jangan yang sensitif.

    <Callout type="warn">
      Di lab, `exp` diset lima menit setelah `iat`. Masa berlaku itu pengaturan keamanan, bukan soal kenyamanan. Karena token self-contained nggak bisa ditarik kembali, umur yang pendek adalah pembatas utama nilai token yang dicuri.
    </Callout>
  </Step>

  <Step id="tradeoff" title="Session atau token?">
    Nggak ada yang otomatis lebih baik. Keduanya cuma memindahkan state ke tempat yang berbeda.

    | | Server session (Module 1) | JWT access token |
    |---|---|---|
    | Sumber kebenaran | Satu baris di tabel session server | Di dalam token yang di-sign |
    | Pengecekan tiap request | Lookup session | Verifikasi signature dan claims |
    | Revoke seketika | Bisa, tinggal hapus barisnya | Nggak bisa sampai `exp` (lesson 6) |
    | Banyak service | Harus berbagi session store | Masing-masing cukup punya public key |
    | Ukuran di jaringan | Id acak yang pendek | Ratusan byte, dikirim di setiap request |
    | Data basi | Selalu terbaru | Claims dibekukan saat token diterbitkan |

    JWT paling masuk akal kalau **lebih dari satu service** harus percaya pada login yang sama, misalnya identity provider dengan beberapa API, atau kalau kamu mau verifikasi tanpa database bersama. Untuk satu web app yang ngobrol dengan backend-nya sendiri, server session biasa sering lebih simpel dan lebih aman.

    <Callout type="info">
      Coba tanyakan ke sistem kamu sendiri: waktu **sso-backend** menerbitkan token yang diterima **core-api**, claims mana yang benar-benar dicek core-api, dan apakah daftarnya sama dengan tabel di atas?
    </Callout>
  </Step>

    1. Perhatikan tiga warnanya: header, payload, signature.
    2. Baca penjelasan di bawah tiap claim (hover juga menampilkannya), dan lihat bagaimana `exp` ditampilkan sebagai waktu relatif.
    3. Ganti teksnya dengan sembarang karakter, atau `a.b.c`, lalu lihat error inline muncul, bukan crash.
