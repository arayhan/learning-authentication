<LessonSteps>
  <Step id="hook" title="Hook">
    JWT cryptography is rarely the weak point. The verifier code around it is. Most real JWT breaches did not break RSA or HMAC: they talked a verifier into **not checking**, using fields the attacker wrote themselves.

    Almost all of it comes down to one mistake: trusting the token to describe how it should be verified.

    <Analogy title="The guard and the checked-by line">
      A guard compares each pass against the list of approved stamps. Then someone hands over a pass with the line "checked by: no one needed". A guard who reads that line and waves them through has let the visitor write the rule.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    A verifier receives bytes from the network and must decide whether to believe them. Every part of the token is **untrusted input** until the signature is checked, and the header is the most dangerous part: it says which algorithm and which key to use.

    <SequenceFlow flow={flows.algNone} />

    The rule that kills the whole class is simple, and it is in RFC 8725, the JWT best current practices:

    1. **Pin the algorithm.** The verifier decides which algorithm it accepts, per issuer. It never uses the token's `alg` to choose.
    2. **Bind the key to the algorithm.** An RSA public key is only ever used for an RSA verification, never handed to an HMAC.
    3. **Validate the claims.** `exp`, `iss` and `aud` are checked every time. A valid signature is where verification starts, not where it ends.

    The lab has two verifiers behind `GET /api/profile`. The default is **secure** and does all three. A request with `X-Lab-Mode: vulnerable` goes to a deliberately broken one, shown below, so you can watch each mistake fail in the real world.
  </Step>

  <Step id="flaws" title="The attack catalogue">
    | Attack | What the attacker controls | Why it works | Defense |
    |---|---|---|---|
    | **`alg: none`** | The `alg` header | The verifier sees `none` and skips the signature | Pin algorithms. Reject `none` |
    | **RS256 to HS256 confusion** | The `alg` header | The verifier uses the RSA **public** key bytes as an HMAC secret, and the attacker knows them | Pin algorithms. Bind each key to one algorithm |
    | **Expired or foreign token** | Nothing: a replayed, genuine token | Only the signature is checked | Require `exp`, `iss` and `aud` |
    | **`kid` injection** | The `kid` header | The server uses `kid` in a file path or an SQL string | Treat `kid` as a lookup into a fixed set. Parameterize queries |
    | **`jku` / `x5u` / `jwk` header** | A URL or a key inside the header | The verifier fetches or trusts the attacker's key | Ignore those headers. Use only your configured JWKS |
    | **Weak HS256 secret** | Nothing | A short secret can be brute-forced offline from one captured token | A random secret of at least 256 bits, or an asymmetric algorithm |
    | **Token in a URL** | Nothing | URLs leak into logs, history and `Referer` | Send it in the `Authorization` header only |

    The first three are the ones you will break in a moment. A few details are worth knowing.

    - **Key confusion** needs the verifier's code to use one `key` value for any algorithm. A library that takes `(token, key)` and lets the token pick the algorithm is exactly that. This is why modern libraries want you to pass the allowed algorithms.
    - **A token for the wrong audience** is a quieter version of the same bug. One issuer often serves many APIs, and without an `aud` check any API's token opens any other.
    - **There is no "just decode" shortcut.** Code that only base64-decodes the payload and reads `sub` is trusting an unsigned note.

    <Callout type="info">
      Worth asking of your own setup: does **core-api** pass an explicit algorithm list to its JWT library, and does it check `iss` and `aud` as well as `exp`? Which library and version does it use, and what are its defaults?
    </Callout>
  </Step>

  <Step id="breakit" title="Break it">
    Three live attacks against the lab. Each card asks the lab to forge a token (the helper `POST /__attack/sign` exists only in vulnerable mode), then sends **the same token** to `GET /api/profile` twice: once to the secure verifier and once to the vulnerable one.

    Click **Run** on each card. You are looking for `401` on the left and `200` on the right.

    <JwtAttackLab />

    What each card shows:

    - **alg: none** was accepted by the vulnerable verifier with no signature at all. The secure verifier rejected it because it only accepts RS256.
    - **Key confusion** was signed with HMAC, using the public key's PEM text as the secret. An attacker can rebuild that text from the public JWKS from lesson 2, so no secret was needed. The secure verifier never performs an HMAC check, so the token fails.
    - **Expired** carries a genuine RS256 signature, only its `exp` is an hour old. The vulnerable verifier never reads `exp`.

    Open the Inspector and look at the `401` rows. They carry `WWW-Authenticate: Bearer error="invalid_token"`, which is how a server tells a client that the token, not the request, was the problem (RFC 6750).

      The vulnerable mode is a switch on the server, so it can be shown. A real API has no such switch, and the same flaws sit in code like the listing below. Reviewing JWT handling means reading it for exactly these four flaws.
    </Callout>
  </Step>
