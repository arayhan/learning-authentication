<LessonSteps>
  <Step id="hook" title="Pembuka">
    Lesson 1 meninggalkan satu masalah. Token self-contained nggak bisa ditarik kembali, jadi harus cepat expired. Tapi nggak ada yang mau ngetik password tiap lima menit.

    Solusinya pakai **dua** token dengan dua tugas berbeda: yang berumur pendek untuk membuka pintu, dan yang berumur panjang yang satu-satunya kekuatannya cuma untuk meminta token pendek yang baru.

    <Analogy title="Tiket harian dan kartu member">
      Pusat kebugaran memberi kamu tiket harian yang ditunjukkan di setiap pintu, dan hangus malam ini. Kartu member tetap di dompet, dan cuma ditunjukkan ke resepsionis untuk dapat tiket besok. Tiket harian hilang, rugi sehari; kartu hilang, resepsionis bisa langsung membatalkannya.
    </Analogy>
  </Step>

  <Step id="concept" title="Konsep">
    | | **Access token** | **Refresh token** |
    |---|---|---|
    | Tugas | Mengotorisasi satu API call | Mendapatkan access token baru |
    | Format di lab | JWT yang di-sign (RS256) | 32 byte acak, opaque |
    | Masa berlaku di lab | 5 menit | 14 hari |
    | Dikirim ke | Setiap API request | Hanya `/refresh` |
    | Dicek lewat | Signature dan claims, tanpa lookup | Lookup database |
    | Bisa di-revoke | Tidak sebelum `exp` | Ya, kapan saja |
    | Disimpan di server | Tidak ada | Hanya sha256-nya |

    Response login di lab menampilkan keduanya, di dua tempat yang semestinya:

    ```text
    HTTP/1.1 200 OK
    Content-Type: application/json
    Cache-Control: no-store
    Set-Cookie: rt=Xk3q9ZmB1v…; Path=/refresh; Max-Age=1209600; HttpOnly; SameSite=Strict

    {"access_token":"eyJhbGci…","token_type":"Bearer","expires_in":300}
    ```

    **Access token** ada di body, jadi kode di halaman bisa memegangnya dan mengirim `Authorization: Bearer <token>`. Header itu didefinisikan di RFC 6750. **Refresh token** ada di cookie yang nggak bisa dibaca JavaScript halaman, dan tiap atributnya ada alasannya:

    | Atribut | Kenapa |
    |---|---|
    | `HttpOnly` | Bug XSS nggak bisa membaca dan menyalin refresh token (lesson 4) |
    | `Path=/refresh` | Browser hanya mengirimnya ke `/refresh` dan `/refresh/logout`, nggak pernah ikut API call biasa |
    | `SameSite=Strict` | Nggak pernah dikirim pada request lintas situs |
    | `Max-Age=1209600` | 14 hari, setelah itu user login lagi |
    | `Secure` | Absen hanya karena lab jalan di `http://localhost`. Di production ini wajib |

    `Cache-Control: no-store` juga penting: response yang membawa token nggak boleh mengendap di cache browser atau proxy.

    <Callout type="info">
      Kenapa refresh token **bukan** JWT? Tujuan utamanya adalah bisa di-revoke dan tinggal di tabel sisi server, jadi nilai acak opaque yang di-lookup server adalah bentuk yang pas. Menyimpan hanya sha256-nya mengikuti aturan Module 1: database yang bocor nggak boleh berisi credential yang bisa dipakai.
    </Callout>
  </Step>

  <Step id="rotation" title="Rotation">
    Refresh token yang hidup 14 hari itu target yang menggiurkan. **Refresh token rotation** memperkecil kerusakannya: setiap kali kamu memakai refresh token, server memensiunkannya dan memberi yang baru.

    <SequenceFlow flow={flows.refreshRotation} />

    Server menyimpan token dalam satu **family**, satu family per login. Setiap pemakaian melakukan ini dalam satu transaksi database:

    1. Cari baris token yang disodorkan, lalu lock.
    2. Kalau sudah **dipakai atau di-revoke**: revoke seluruh family dan balas 401.
    3. Kalau belum, tandai sudah dipakai, masukkan penggantinya di family yang sama, lalu kembalikan access token baru dan cookie baru.

    Langkah 2 adalah **reuse detection**. Kalau pencuri dan user asli sama-sama memegang token 1, siapa pun yang refresh belakangan menyodorkan token yang sudah terpakai. Server nggak bisa tahu mana yang pencuri, jadi dia me-revoke family. Keduanya harus login ulang, dan si pencuri tersingkir. OAuth 2.0 Security Best Current Practice (RFC 9700) merekomendasikan ini untuk refresh token.

    <Callout type="warn">
      Rotation punya biaya nyata. Dua tab yang refresh bersamaan, atau retry setelah response hilang, bisa menyodorkan token yang sama dua kali dan terlihat persis seperti pencurian. Sistem production biasanya menserialisasi refresh di sisi client atau memberi grace window yang sangat pendek untuk token sebelumnya. Lab ini me-lock baris (`FOR UPDATE`) sehingga hanya satu dari dua refresh bersamaan yang menang, dan yang kalah dianggap reuse.
    </Callout>
  </Step>

    1. Klik **Login**. Body-nya berisi access token. Buka baris `POST /login` di Inspector dan lihat tab **Cookies**: `rt` dengan `HttpOnly`, `Path=/refresh`, dan `SameSite=Strict`.
    2. Klik **Profile**. Console mengirim `Authorization: Bearer <token kamu>` secara otomatis dan API membalas `200`.
    3. Klik **Profile, tanpa token**. Jawabannya `401` dengan `WWW-Authenticate: Bearer`: sama sekali nggak ada credential, sesuai permintaan RFC 6750. Token yang ada tapi salah akan mendapat `error="invalid_token"`.
    4. Klik **Refresh**. Browser menyertakan cookie tanpa bantuan halaman. Kamu dapat access token baru dan `rt` **baru** di `Set-Cookie`. Yang lama sekarang sudah terpakai.

    Kamu nggak pernah mengetik atau menyalin refresh token, dan script di halaman pun nggak bisa: dia HttpOnly.

  <Step id="reuse" title="Reuse detection">
    Browser nggak akan membiarkan kamu memutar ulang cookie lama, jadi di bagian ini berperanlah jadi pencuri pakai `curl`. Pakai port dari implementasi yang kamu pilih: `4102` untuk Go, `4202` untuk TypeScript. Jalankan di Git Bash, WSL, atau shell POSIX apa saja.

    ```bash
    LAB=http://localhost:4102
    # log in and keep the cookie jar
    curl -s -c jar.txt -X POST $LAB/login -H 'Content-Type: application/json' \
      -d '{"email":"alice@example.com","password":"correct-horse-battery"}' > /dev/null
    # copy the refresh token out of the jar (a thief would get it by other means)
    RT=$(awk '$6=="rt"{print $7}' jar.txt)

    # first use: 200, new access token, new rt
    curl -s -o /dev/null -w '%{http_code}\n' -X POST $LAB/refresh -H "Cookie: rt=$RT"
    # second use of the SAME token: 401, and the whole family is revoked
    curl -s -o /dev/null -w '%{http_code}\n' -X POST $LAB/refresh -H "Cookie: rt=$RT"
    ```

    Panggilan kedua mencetak `401`. Lihat Inspector: `POST /refresh` pertama mengembalikan 200, yang kedua 401, dan lab task di atas tercentang.

    Panggilan pertama juga menerbitkan token pengganti. Panggilan kedua me-revoke seluruh family, jadi token pengganti itu ikut mati dan user asli ikut ter-logout. Memang itu hasil yang diinginkan: token yang disalin membuat kedua pihak kehilangan session, dan user baru sadar saat refresh berikutnya.
  </Step>
