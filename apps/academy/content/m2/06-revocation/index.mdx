<LessonSteps>
  <Step id="hook" title="Pembuka">
    User klik **Logout**. Atau support menonaktifkan sebuah akun. Atau ada yang melapor laptopnya dicuri. Pasti semua token milik user itu langsung berhenti berfungsi, kan?

    Nggak untuk token self-contained. Ini harga dari desain di lesson 1, dan ini jawaban salah yang paling sering muncul di interview JWT: "ya tinggal kita hapus aja pas logout".

    <Analogy title="Kartu yang sudah diblokir di toko offline">
      Bank memblokir kartu kamu yang hilang, tapi toko yang mesin EDC-nya sedang offline cuma mengecek tanggal berlaku di kartu. Kartunya tetap diterima dengan senang hati sampai tanggal itu lewat. Cara menutup celahnya cuma dua: masa berlaku yang pendek, atau toko yang telepon bank dulu.
    </Analogy>
  </Step>

  <Step id="concept" title="Konsep">
    API yang memverifikasi JWT secara offline nggak bertanya ke siapa pun. Apa pun yang dilakukan server setelah menerbitkan token nggak bisa menjangkaunya: token valid sampai `exp`, dan itu memang disengaja.

    <SequenceFlow flow={flows.revocation} />

    Jadi "logout" sebenarnya berarti dua hal berbeda, dan sebaiknya dipisahkan.

    | | Yang dilakukan | Efek |
    |---|---|---|
    | **Revoke refresh token** | Menandai refresh family sebagai revoked dan menghapus cookie | Access token baru nggak bisa diterbitkan lagi. Berlaku seketika |
    | **Access token expiry** | Token habis sendiri | Paling lama `expires_in` detik kemudian: 5 menit di lab |

    Logout baru tuntas setelah sisa umur access token habis. Client juga sebaiknya membuang salinannya, tapi itu nggak melindungi apa pun dari orang yang sudah menyalinnya.

    Claims juga basi dengan cara yang sama. Kalau user diturunkan perannya atau dinonaktifkan, token yang diterbitkan sebelumnya masih menyebut peran lama sampai expired.
  </Step>

  <Step id="strategies" title="Strategi">
    Ada beberapa pilihan, dan semuanya memunculkan kembali sebagian state.

    | Strategi | Cara kerja | Biaya |
    |---|---|---|
    | **Umur pendek** | Terima ketidakbaruan datanya: `exp` tinggal beberapa menit | Refresh lebih sering. Batas bawah risikonya nggak pernah nol |
    | **Revoke refresh token** (yang dipakai lab) | Hapus atau tandai refresh family | Access token tetap hidup sampai `exp` |
    | **Deny list** | Simpan nilai `jti` atau session id yang di-revoke, lalu cek tiap request | Satu lookup per call. Entri cukup hidup sampai `exp` |
    | **Token introspection** | API bertanya ke authorization server apakah token masih aktif (RFC 7662) | Satu network call per request, dan dependency saat runtime |
    | **"Valid after" per user** | Simpan satu timestamp per user, tolak token dengan `iat` yang lebih lama | Satu lookup kecil per request. Memberi "logout di semua perangkat" dan "password diganti" |
    | **Opaque reference token** | Jangan pakai JWT: token berupa id acak yang di-lookup di setiap call | Kembali ke session Module 1, lengkap dengan semua sifatnya |

    Default yang masuk akal adalah dua yang pertama digabung, dan itulah yang dilakukan lab. Tambahkan deny list atau pengecekan "valid after" hanya di tempat yang jendela lima menit terlalu panjang, seperti konsol admin atau pembayaran.

    <Callout type="warn">
      Jangan mengandalkan client. Permintaan untuk menghapus token dari `localStorage` hanya membantu halaman yang jujur. Token yang sudah disalin tetap berfungsi, jadi revoke yang sebenarnya harus terjadi di server.
    </Callout>

    <Callout type="info">
      Coba tanyakan ke sistem kamu sendiri: ketika akun dinonaktifkan di **sso-backend**, berapa lama token yang sudah diterbitkan masih bisa dipakai di **core-api**? Apa yang membatasinya, dan adakah pengecekan di antaranya?
    </Callout>
  </Step>

  <Step id="lab" title="Lab">
    Logout dan perhatikan apa yang berhenti berfungsi, dan apa yang tidak.

    <LabTasks />

    <LabConsole
      lab="02"
      actions={[
        { label: "Login", method: "POST", path: "/login", body: { email: "alice@example.com", password: "correct-horse-battery" } },
        { label: "Profile", method: "GET", path: "/api/profile", headers: { Authorization: "Bearer {{accessToken}}" } },
        { label: "Logout", method: "POST", path: "/refresh/logout" },
        { label: "Refresh", method: "POST", path: "/refresh" },
      ]}
    />

    1. Klik **Login**, lalu **Profile**: `200`.
    2. Klik **Logout**. Jawabannya `204 No Content` dan satu `Set-Cookie` yang menghapus `rt`. Logout berupa `POST` ke `/refresh/logout` karena cookie refresh hanya dikirim ke path di bawah `/refresh`.
    3. Klik **Refresh**. Hasilnya `401`: cookie sudah hilang dan family-nya di-revoke.
    4. Klik **Profile** lagi. Hasilnya masih **`200`**. Console menyimpan access token dari login kamu, dan API nggak punya alasan meragukannya sampai expired. Itulah celah dari tabel di atas, secara live.

    Browser sudah menghapus cookie-nya, jadi langkah 3 tiba tanpa cookie. Untuk melihat revoke **di sisi server** atas token yang *disalin* seseorang, pakai curl lagi (port `4102` untuk Go, `4202` untuk TypeScript):

    ```bash
    LAB=http://localhost:4102
    curl -s -c jar.txt -X POST $LAB/login -H 'Content-Type: application/json' \
      -d '{"email":"alice@example.com","password":"correct-horse-battery"}' > /dev/null
    RT=$(awk '$6=="rt"{print $7}' jar.txt)

    curl -s -o /dev/null -w 'logout: %{http_code}\n'  -X POST $LAB/refresh/logout -H "Cookie: rt=$RT"
    curl -s -o /dev/null -w 'refresh with the copied token: %{http_code}\n' -X POST $LAB/refresh -H "Cookie: rt=$RT"
    ```

    Salinannya masih punya byte yang benar, tapi ditolak: `204`, lalu `401`.
  </Step>
