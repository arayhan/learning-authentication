<LessonSteps>
  <Step id="hook" title="Hook">
    A user clicks **Log out**. Or support disables an account. Or someone reports a stolen laptop. Surely every token for that user stops working right now?

    Not with a self-contained token. This is the price of lesson 1's design, and it is the most common wrong answer in JWT interviews: "we just delete it on logout".

    <Analogy title="The cancelled card at an offline shop">
      The bank cancels your lost card, but a shop with no network connection checks only the printed expiry date. It happily accepts the card until that date passes. The only ways to close the gap are short expiry dates, or shops that phone the bank.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    An API that verifies a JWT offline asks nobody. Nothing the server does after issuing the token can reach it: the token is valid until `exp`, and that is by design.

    <SequenceFlow flow={flows.revocation} />

    So "logout" really means two different things, and it helps to keep them apart.

    | | What it does | Effect |
    |---|---|---|
    | **Refresh token revocation** | Marks the refresh family revoked and clears the cookie | No new access tokens can be issued. Takes effect at once |
    | **Access token expiry** | The token simply runs out | Up to `expires_in` seconds later: 5 minutes in the lab |

    The logout is complete after the access token's remaining lifetime. A client should also throw its copy away, but that protects nothing against someone who already copied it.

    Claims go stale in the same way. If a user is demoted or disabled, a token issued before that still says the old role until it expires.
  </Step>

  <Step id="strategies" title="Strategies">
    There is a menu, and every item reintroduces some state.

    | Strategy | How it works | Cost |
    |---|---|---|
    | **Short lifetime** | Accept the staleness: `exp` is minutes away | More refreshes. The floor on exposure never reaches zero |
    | **Revoke the refresh token** (the lab) | Delete or mark the refresh family | Access tokens still live until `exp` |
    | **Deny list** | Store revoked `jti` values, or session ids, and check each request | A lookup per call. Entries only need to live until `exp` |
    | **Token introspection** | The API asks the authorization server whether the token is active (RFC 7662) | A network call per request, and a runtime dependency |
    | **"Valid after" per user** | Store one timestamp per user, reject tokens with an older `iat` | One small lookup per request. Gives "log out everywhere" and "password changed" |
    | **Opaque reference tokens** | Do not use a JWT: the token is a random id looked up on each call | Back to Module 1's sessions, with all their properties |

    A reasonable default is the first two together, which is what the lab does. Add a deny list or a "valid after" check only where a five-minute window is too long, such as admin consoles or payments.

    <Callout type="warn">
      Do not rely on the client. A request to delete the token from `localStorage` only helps an honest page. A copied token keeps working, so real revocation has to happen on the server.
    </Callout>

    <Callout type="info">
      Worth asking of your own system: when an account is disabled in **sso-backend**, how long can an already-issued token still be used on **core-api**? What bounds that, and is there any check in between?
    </Callout>
  </Step>

  <Step id="lab" title="Lab">
    Log out and watch what stops working, and what does not.

    <LabTasks />

    <LabConsole
      lab="02"
      actions={[
        { label: "Log in", method: "POST", path: "/login", body: { email: "alice@example.com", password: "correct-horse-battery" } },
        { label: "Profile", method: "GET", path: "/api/profile", headers: { Authorization: "Bearer {{accessToken}}" } },
        { label: "Log out", method: "POST", path: "/refresh/logout" },
        { label: "Refresh", method: "POST", path: "/refresh" },
      ]}
    />

    1. Click **Log in**, then **Profile**: `200`.
    2. Click **Log out**. The answer is `204 No Content` and a `Set-Cookie` that deletes `rt`. Logout is a `POST` to `/refresh/logout` because the refresh cookie is only sent to paths under `/refresh`.
    3. Click **Refresh**. It returns `401`: the cookie is gone and the family is revoked.
    4. Click **Profile** again. It still returns **`200`**. The console kept the access token from your login, and the API has no reason to doubt it until it expires. That is the gap from the table above, live.

    The browser deleted the cookie, so step 3 arrives without one. To see the **server-side** revocation of a token someone *copied*, use curl again (port `4102` for Go, `4202` for TypeScript):

    ```bash
    LAB=http://localhost:4102
    curl -s -c jar.txt -X POST $LAB/login -H 'Content-Type: application/json' \
      -d '{"email":"alice@example.com","password":"correct-horse-battery"}' > /dev/null
    RT=$(awk '$6=="rt"{print $7}' jar.txt)

    curl -s -o /dev/null -w 'logout: %{http_code}\n'  -X POST $LAB/refresh/logout -H "Cookie: rt=$RT"
    curl -s -o /dev/null -w 'refresh with the copied token: %{http_code}\n' -X POST $LAB/refresh -H "Cookie: rt=$RT"
    ```

    The copy still has the right bytes, and it is refused: `204`, then `401`.
  </Step>
