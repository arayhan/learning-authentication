<LessonSteps>
  <Step id="hook" title="Pembuka">
    Lesson 1 bilang signature yang bikin JWT bisa dipercaya. Tapi dipercaya oleh *siapa*? API harus mengecek signature itu, dan pengecekannya butuh key. Gimana caranya selusin service dapat key itu tanpa ikut punya kuasa untuk memalsukan token?

    Jawabannya **asymmetric signature**: satu key untuk men-sign, key lain yang publik untuk memverifikasi. Publikasikan yang publik di URL yang sudah dikenal, dan verifikasi bisa dilakukan siapa saja.

    <Analogy title="Stempel RT dan buku contoh stempel">
      Pak RT punya stempel yang cuma bisa dibuat dari cap asli miliknya. Semua warga punya buku contoh stempel itu, jadi siapa pun bisa membandingkan, tapi nggak ada yang bisa bikin cap baru yang sama persis. Kalau Pak RT ganti stempel, tinggal perbarui buku contohnya.
    </Analogy>
  </Step>

  <Step id="concept" title="Konsep">
    Signing berjalan dalam dua langkah. Issuer menyusun **signing input**, yaitu `base64url(header) + "." + base64url(payload)`, lalu men-sign-nya dengan private key. Verifier menghitung ulang pengecekan signature dengan key yang dia percaya, lalu membandingkan.

    Pertanyaannya: key itu datang dari mana? Verifier nggak boleh mengambilnya dari token, karena itu input attacker. Key harus datang dari tempat yang dipercaya verifier, dan di kebanyakan sistem tempat itu adalah **JWKS** (JSON Web Key Set, RFC 7517) yang dipublikasikan issuer.

    <SequenceFlow flow={flows.jwksVerify} />

    Perhatikan siapa melakukan apa. API mengambil key set, memilih key yang disebut `kid` di token, lalu memverifikasi. API sama sekali nggak memegang apa pun yang bisa men-sign.
  </Step>

  <Step id="algorithms" title="Algoritma signature">
    Header `alg` menyebut algoritmanya (RFC 7518). Ada tiga yang perlu kamu kenal.

    | Algoritma | Jenis | Siapa yang bisa verify | Siapa yang bisa sign | Ukuran signature | Pakai kalau |
    |---|---|---|---|---|---|
    | **HS256** | HMAC dengan shared secret | Siapa saja yang punya secret | Siapa saja yang punya secret | 32 byte | Satu service menerbitkan dan memverifikasi token-nya sendiri |
    | **RS256** | Signature RSA, SHA-256 | Siapa saja yang punya public key | Hanya pemegang private key | 256 byte (key 2048-bit) | Banyak verifier, dukungan library paling luas. Lab ini memakainya |
    | **ES256** | ECDSA di P-256, SHA-256 | Siapa saja yang punya public key | Hanya pemegang private key | 64 byte | Banyak verifier, dan token lebih kecil serta cepat |

    Pertanyaan penentunya: **siapa yang perlu memverifikasi**. HS256 nggak punya sisi publik: setiap service yang bisa verify juga bisa memalsukan. Itu aman di dalam satu service, tapi salah untuk banyak service. Dengan RS256 dan ES256, API yang bobol cuma membocorkan public key.

    <Callout type="warn">
      Jangan pilih algoritma cuma karena tutorial-nya begitu. Pilih berdasarkan bentuk trust-nya, lalu **pin** di verifier (lesson 5). Hindari juga `none`, yang artinya tanpa signature sama sekali. RFC 8725 bilang verifier harus menolaknya kecuali aplikasi memang mengharapkan token tanpa signature.
    </Callout>
  </Step>

  <Step id="jwks" title="Mempublikasikan key">
    **JWK** adalah key yang ditulis sebagai JSON, dan **JWKS** adalah `{"keys":[…]}`. Ini bentuk yang disajikan lab:

    ```json
    {
      "keys": [
        { "kty": "RSA", "n": "0vx7ag…", "e": "AQAB", "kid": "k3Hq9ZmB1vW8eYrT", "alg": "RS256", "use": "sig" }
      ]
    }
    ```

    | Field | Arti |
    |---|---|
    | `kty` | Tipe key: di sini `RSA` |
    | `n`, `e` | Public key RSA: modulus dan exponent, dalam base64url |
    | `kid` | Id key. Header `kid` di token memilih entri ini |
    | `alg`, `use` | Algoritma yang dimaksud, dan `sig` untuk signing |

    Inilah gunanya `kid`. Satu set bisa berisi beberapa key sekaligus, dan begitulah **key rotation** berjalan tanpa downtime:

    1. Tambahkan key baru ke JWKS.
    2. Mulai men-sign dengan `kid` baru. Token lama tetap lolos verifikasi, karena key lamanya masih tercantum.
    3. Tunggu sampai masa berlaku token terpanjang, plus cache, terlewati.
    4. Hapus key lama.

    Verifier me-**cache** JWKS dan baru mengambil ulang saat ketemu `kid` yang asing, dengan rate limit. Kalau diambil di setiap request, identity provider kamu jadi bottleneck sekaligus single point of failure.

    <Callout type="security">
      Percayai JWKS hanya dari URL yang **kamu** konfigurasi untuk issuer. Jangan pernah mengikuti header `jku` atau `x5u` di dalam token untuk mengambil key: itu membuat attacker bisa mengarahkan kamu ke key set miliknya sendiri. RFC 8725 memperingatkan hal ini.
    </Callout>

    <Callout type="info">
      Coba tanyakan ke setup kamu sendiri: dari mana **core-api** mendapat key untuk memverifikasi token dari **sso-backend**? JWKS yang diambil dan di-cache dengan refetch saat `kid` asing, key yang ditempel di config, atau shared secret?
    </Callout>
  </Step>
