<LessonSteps>
  <Step id="hook" title="Hook">
    Lesson 1 said the signature makes a JWT trustworthy. But trustworthy to *whom*? The API has to check that signature, and checking needs a key. How does a dozen services get that key without also getting the power to forge tokens?

    The answer is **asymmetric signatures**: one key signs, a different, public key verifies. Publish the public one on a well-known URL and verification scales to anyone.

    <Analogy title="The wax seal and the seal catalogue">
      A king presses a wax seal that only his ring can make. Everyone has the catalogue of royal seals, so anyone can compare, but nobody can make a new impression. Updating the catalogue is how a new ring is introduced.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    Signing works in two steps. The issuer builds the **signing input**, `base64url(header) + "." + base64url(payload)`, and signs it with a private key. A verifier recomputes the signature check with a key it trusts and compares.

    Where the key comes from is the question. The verifier cannot take it from the token: that is the attacker's input. It must come from somewhere the verifier trusts, and for most systems that place is a **JWKS** (JSON Web Key Set, RFC 7517) published by the issuer.

    <SequenceFlow flow={flows.jwksVerify} />

    Notice who does what. The API fetches the key set, picks the key named by the token's `kid`, and verifies. The API never holds anything that can sign.
  </Step>

  <Step id="algorithms" title="Signature algorithms">
    The `alg` header names the algorithm (RFC 7518). Three are worth knowing.

    | Algorithm | Kind | Who can verify | Who can sign | Signature size | Reach for it when |
    |---|---|---|---|---|---|
    | **HS256** | HMAC with a shared secret | Anyone with the secret | Anyone with the secret | 32 bytes | One service both issues and verifies its own tokens |
    | **RS256** | RSA signature, SHA-256 | Anyone with the public key | Only the private key holder | 256 bytes (2048-bit key) | Many verifiers, widest library support. The lab uses this |
    | **ES256** | ECDSA on P-256, SHA-256 | Anyone with the public key | Only the private key holder | 64 bytes | Many verifiers and smaller, faster tokens |

    The deciding question is **who needs to verify**. HS256 has no public half: every service that can verify can also forge. That is fine inside one service and wrong across a fleet. With RS256 and ES256, a compromised API leaks only a public key.

    <Callout type="warn">
      Do not pick an algorithm because a tutorial did. Pick it from the trust shape, and then **pin it** in the verifier (lesson 5). Also avoid `none`, which means no signature at all. RFC 8725 says a verifier must reject it unless the application really expects unsigned tokens.
    </Callout>
  </Step>

  <Step id="jwks" title="Publishing keys">
    A **JWK** is a key written as JSON, and a **JWKS** is `{"keys":[…]}`. Here is the shape the lab serves:

    ```json
    {
      "keys": [
        { "kty": "RSA", "n": "0vx7ag…", "e": "AQAB", "kid": "k3Hq9ZmB1vW8eYrT", "alg": "RS256", "use": "sig" }
      ]
    }
    ```

    | Field | Meaning |
    |---|---|
    | `kty` | Key type: `RSA` here |
    | `n`, `e` | The RSA public key: modulus and exponent, base64url |
    | `kid` | The key's id. A token's `kid` header selects this entry |
    | `alg`, `use` | The intended algorithm, and `sig` for signing |

    This is why `kid` exists. A set can hold several keys at once, and that is how **key rotation** works without an outage:

    1. Add the new key to the JWKS.
    2. Start signing with the new `kid`. Old tokens still verify, because the old key is still listed.
    3. Wait for the longest token lifetime, plus caches, to pass.
    4. Remove the old key.

    Verifiers **cache** the JWKS and refetch only when they meet an unknown `kid`, with a rate limit. Fetching it on every request would make your identity provider a bottleneck and a single point of failure.

    <Callout type="security">
      Only trust a JWKS from a URL **you** configured for the issuer. Never follow a `jku` or `x5u` header inside the token to fetch keys: that lets an attacker point you at their own key set. RFC 8725 warns against it.
    </Callout>

    <Callout type="info">
      Worth asking of your own setup: where does **core-api** get the key to verify tokens from **sso-backend**? Is it a fetched, cached JWKS with a refetch on unknown `kid`, a key pasted into config, or a shared secret?
    </Callout>
  </Step>
