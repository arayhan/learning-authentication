<LessonSteps>
  <Step id="hook" title="Pembuka">
    Sekarang kamu punya dua token, dan browser cuma menyediakan empat tempat untuk menaruhnya: `localStorage`, `sessionStorage`, variabel di memory, atau cookie. Setiap tutorial memilih salah satu, dan kebanyakan nggak bilang apa harganya.

    Jawaban jujurnya bergantung pada satu pertanyaan: apa yang bisa dilakukan attacker kalau script buatannya jalan di dalam halaman kamu? Serangan itu namanya **XSS (cross-site scripting)**, dan itulah alasan lesson ini ada.

    <Analogy title="Dompet dan sticky note PIN">
      Dompet di saku celana butuh orang yang merogoh sakumu. Sticky note berisi PIN yang ditempel di pintu depan bisa dibaca semua orang yang lewat. Di mana kamu menyimpan rahasia menentukan siapa yang bisa mengambilnya.
    </Analogy>
  </Step>

  <Step id="concept" title="Konsep">
    JavaScript apa pun yang jalan di halaman kamu berjalan dengan **semua** hak akses halaman itu. Dia bisa membaca `localStorage`, memanggil API kamu, dan mengirim data ke server mana pun. Nggak penting bagaimana script itu sampai di sana: kolom komentar yang nggak meng-escape HTML, dependency npm yang kena kompromi, atau iklan pihak ketiga.

    <SequenceFlow flow={flows.xssTheft} />

    Dari sini muncul dua hal, dan arahnya berlawanan.

    1. Token yang **bisa dibaca** JavaScript bisa dicuri dan dipakai ulang dari mesin attacker sendiri, dengan santai, sampai expired.
    2. Token yang disertakan browser **secara otomatis** (cookie) terbuka terhadap request palsu dari situs lain. Itu CSRF, dari Module 1.

    Jadi nggak ada storage yang aman dari segalanya. Tujuannya adalah memilih risiko mana yang kamu ambil untuk tiap token, dan menjaga jendela token curian tetap kecil.
  </Step>

  <Step id="options" title="Pilihan yang ada">
    | Tempat | Bisa dibaca script XSS? | Dikirim otomatis (CSRF)? | Bertahan setelah reload? | Kesimpulan |
    |---|---|---|---|---|
    | `localStorage` | **Ya** | Tidak | Ya, di semua tab | Hindari untuk token |
    | `sessionStorage` | **Ya** | Tidak | Hanya di tab itu | Hindari untuk token |
    | Variabel di memory | Tidak langsung | Tidak | Tidak: hilang saat reload | Bagus untuk **access** token |
    | Cookie `HttpOnly` | **Tidak** | **Ya** | Ya | Bagus untuk **refresh** token, dengan `SameSite` dan `Path` yang sempit |

    Dari situ lahir pola yang dipakai Lab 02:

    - **Access token** hidup hanya di variabel JavaScript di dalam kode aplikasi kamu sendiri. Dia nggak pernah ditulis ke storage, jadi nggak ada yang bisa dibaca script dari storage, dan umurnya memang pendek.
    - **Refresh token** hidup di cookie `HttpOnly; SameSite=Strict` dengan scope `Path=/refresh`. JavaScript nggak bisa membacanya. Browser hanya mengirimnya ke endpoint refresh.
    - Saat halaman dimuat, belum ada access token di memory. Aplikasi memanggil `POST /refresh`, cookie ikut terkirim, dan access token baru kembali. Reload cuma butuh satu request, bukan login ulang.

    ```js
    let accessToken = null; // module scope: not on window, not in storage

    async function refresh() {
      const res = await fetch("/refresh", { method: "POST", credentials: "include" });
      if (!res.ok) return signOut();
      accessToken = (await res.json()).access_token;
    }

    async function api(path) {
      const call = () => fetch(path, { headers: { Authorization: `Bearer ${accessToken}` } });
      let res = await call();
      if (res.status === 401) { await refresh(); res = await call(); }
      return res;
    }
    ```

    <Callout type="warn">
      **XSS tetap bisa memakai session selama halaman terbuka.** Script suntikan bisa memanggil API kamu, dan bisa memanggil `POST /refresh`: browser menyertakan cookie HttpOnly untuknya dan script menerima access token baru. Dia bahkan bisa mengirim access token itu ke attacker, tapi hanya berlaku sampai expired (5 menit di sini). Yang nggak bisa dilakukan adalah membawa kabur refresh token, jadi kerusakannya berakhir saat tab ditutup atau session di-revoke, bukan bertahan 14 hari.
    </Callout>

    Refresh token yang dibawa cookie memunculkan lagi pertanyaan CSRF. Lab menjawabnya dengan `SameSite=Strict` dan `Path=/refresh`, dan setup production sebaiknya juga mengecek header `Origin` di `/refresh`. Request palsu nggak bisa membaca response, jadi paling parah dia cuma memicu satu rotation.

    <Callout type="info">
      Opsi paling kuat adalah nggak menaruh token di browser sama sekali. Di desain **backend-for-frontend (BFF)**, browser hanya punya cookie session HttpOnly biasa, dan server milik kamu yang memegang token serta memanggil API. Bagian yang bergerak lebih banyak, tapi nggak ada yang bisa dicuri di halaman. Module 3 membahas ini lagi untuk OAuth.
    </Callout>

    <Callout type="info">
      Coba tanyakan ke setup kamu sendiri: di mana **sso-frontend** menyimpan token yang dia dapat dari **sso-backend**? Storage, memory, atau cookie, dan itu baris mana di tabel di atas?
    </Callout>
  </Step>
