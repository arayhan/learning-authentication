<LessonSteps>
  <Step id="hook" title="Hook">
    You have two tokens now, and the browser gives you exactly four places to put them: `localStorage`, `sessionStorage`, a variable in memory, or a cookie. Every tutorial picks one, and most do not say what it costs.

    The honest answer depends on one question: what can the attacker do when a script they wrote runs inside your page? That attack is **XSS (cross-site scripting)**, and it is the reason this lesson exists.

    <Analogy title="The wallet and the taped note">
      A wallet in your pocket needs someone to reach into your pocket. A note with your PIN taped to the front door can be read by everyone who walks by. Where you keep a secret decides who can get at it.
    </Analogy>
  </Step>

  <Step id="concept" title="Concept">
    Any JavaScript that runs on your page runs with **all** of your page's privileges. It can read `localStorage`, call your API, and send data to any server. It does not matter how the script got there: a comment field that did not escape HTML, a compromised npm dependency, a third-party ad.

    <SequenceFlow flow={flows.xssTheft} />

    Two things follow, and they pull in opposite directions.

    1. A token that JavaScript **can read** can be stolen and replayed from the attacker's own machine, at leisure, until it expires.
    2. A token the browser attaches **by itself** (a cookie) is exposed to forged requests from other sites. That is CSRF, from Module 1.

    So there is no storage that is safe against everything. The goal is to choose which risk you take for each token, and to keep the stolen-token window small.
  </Step>

  <Step id="options" title="The options">
    | Where | Readable by an XSS script? | Sent automatically (CSRF)? | Survives a reload? | Verdict |
    |---|---|---|---|---|
    | `localStorage` | **Yes** | No | Yes, in every tab | Avoid for tokens |
    | `sessionStorage` | **Yes** | No | Only in that tab | Avoid for tokens |
    | In-memory variable | Not directly | No | No: gone on reload | Good for the **access** token |
    | `HttpOnly` cookie | **No** | **Yes** | Yes | Good for the **refresh** token, with `SameSite` and a narrow `Path` |

    That gives the pattern Lab 02 uses:

    - The **access token** lives only in a JavaScript variable inside your app's own code. It is never written to storage, so there is nothing for a script to read from storage, and it is short-lived anyway.
    - The **refresh token** lives in an `HttpOnly; SameSite=Strict` cookie scoped to `Path=/refresh`. JavaScript cannot read it. The browser sends it only to the refresh endpoint.
    - On page load there is no access token in memory yet. The app calls `POST /refresh`, the cookie rides along, and a new access token comes back. A reload costs one request, not a login.

    ```js
    let accessToken = null; // module scope: not on window, not in storage

    async function refresh() {
      const res = await fetch("/refresh", { method: "POST", credentials: "include" });
      if (!res.ok) return signOut();
      accessToken = (await res.json()).access_token;
    }

    async function api(path) {
      const call = () => fetch(path, { headers: { Authorization: `Bearer ${accessToken}` } });
      let res = await call();
      if (res.status === 401) { await refresh(); res = await call(); }
      return res;
    }
    ```

    <Callout type="warn">
      **XSS can still use the session while the page is open.** The injected script can call your API, and it can call `POST /refresh`: the browser attaches the HttpOnly cookie for it and the script receives a fresh access token. What it cannot do is carry the refresh token away. So the damage ends when the tab closes or you revoke the session, instead of lasting 14 days.
    </Callout>

    A cookie-carried refresh token raises the CSRF question again. The lab answers it with `SameSite=Strict` and `Path=/refresh`, and a production setup should also check the `Origin` header on `/refresh`. A forged request cannot read the response, so the worst it could do is trigger a rotation.

    <Callout type="info">
      The strongest option is not to put tokens in the browser at all. In a **backend-for-frontend (BFF)** design the browser only has an ordinary HttpOnly session cookie, and a server of yours holds the tokens and calls the APIs. It is more moving parts, but nothing stealable is left in the page. Module 3 returns to this for OAuth.
    </Callout>

    <Callout type="info">
      Worth asking of your own setup: where does the **sso-frontend** keep the token it gets from **sso-backend**? Storage, memory or a cookie, and which row of the table above is that?
    </Callout>
  </Step>
